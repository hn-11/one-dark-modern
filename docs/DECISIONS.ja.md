# 決定事項の記録

> English: [DECISIONS.md](DECISIONS.md)

本書は、配色の選定において議論のあった論点をトークンファミリーごとに記録し、過去に是正された判断ミスの経緯をまとめたものである。各項目は結論となる決定事項を冒頭に示し、その根拠と歴史的経緯を記載している。後の決定が以前の決定を置き換えているケースがあるため、判明しているものについては決定日を明記している。

これらの決定の拠り所となっている基本原則は [PHILOSOPHY.ja.md](PHILOSOPHY.ja.md) に記載されている（本文中では「設計哲学 §4」のように参照）。今後新たな論点に決着がついた場合は、本ドキュメントに追記すること。

## 1. 演算子

記号演算子はすべての言語でシアン `#56B6C2` とする（2026-07-20 決定）。演算子ファミリーを分割しているリファレンスは存在しない。TextMate 時代の Atom は演算子すべてを紫色、後期の Atom は前景色（未着色）、Zed はすべてシアン、base16 は演算子を base05（前景色）に分類していた。エコシステム全体の調査でもシアンは有力な選択肢（前景色、シアン、紫色）の 1 つであり、akamud や One Dark Pro.nvim も同様である。一方、One Dark Pro は混在した配色（論理演算子はシアン、三項演算子やオプショナルチェイニングは単語演算子グループ経由で紫色、アロー関数は紫色、残りは前景色）を出荷していたが、由来の検証を通過できず一括で廃止した。当初はすべて前景色とする案を採用してリリースしたが、コントラストを失った演算子は日常的な開発環境での視認性に耐えられず、同日のうちに即座に撤回し、Zed と同じ「すべてシアン」を採用した。

`=>` は演算子として扱い、キーワードとしては扱わない（2026-07-20 決定）。TextMate-Atom や One Dark Pro の紫色のアローは、近代的なリファレンスに反する。公式 tree-sitter クエリでは `"=>"` を他の記号演算子と同じ `@operator` キャプチャに分類している。

単語演算子（`new`、`typeof`、`instanceof`、`in`、`of`、`delete`、`void`、および Python の `and`/`or`/`not`）は紫色のキーワード色を維持する。単語はキーワード、記号は演算子と明確に分離し、各ファミリー内の一貫性を保つ。

型注釈のコロン `:`、オプショナルの `?`、ユニオン型の `|` など、型領域の記号は前景色（未着色）のままとする。Zed はこれらを `punctuation.special` として暗赤色に設定しているが、Zed 独自の設計判断であるため本テーマには取り入れない。

Go の演算子は単一のシアンファミリー（`:=` `+` `*` `&` `&&` `==`）に統合した。One Dark Pro には Go 特有の不自然な例外が 2 点あった。`:=` の黄色（2018 年の理由未記載のコミット由来）と、ポインタ記号の紫色（2020 年のバグ修正由来）である。これらは両方とも廃止した。後に汎用演算子の見直しで Go の `&&` が意図せず前景色になりかけた際は、`.go` スコープ専用ルールを追加してシアンの一貫性を維持した。

セマンティックハイライトの `operator` エントリは定義しない。rust-analyzer などの言語サーバーが TextMate による言語ごとの演算子配色を上書きして均一化してしまう問題があったため、設計哲学 §5（レイヤリング原則）に従って削除した。

## 2. 定数とリテラル

名前付き定数はオレンジ色の値ファミリーに統合した（2026-07-20 決定）。`const` ローカル変数、SCREAMING_SNAKE_CASE 定数、列挙メンバ、および `Math.PI` や `JSON` のようなプラットフォーム組み込み定数は、数値や真偽値と同じ `#D19A66` を適用する。この統合以降、黄色が表すものは型ファミリーのみとなった。従来の黄色への分割は One Dark Pro 特有の仕様であり、他の系統には見られない。エコシステム全体で定数を分割している数少ないテーマでもシアンや紫色が使われており、base16 では定数とリテラルをまとめて base09 に分類している。統合当初は `variable.defaultLibrary` が黄色に残っていたが、`JSON` に対する 3 件のフリッカー違反として検知され、リリース前の監査によって修正が適用された。

`nil`、`null`、`None` はリテラルであるためオレンジ色を適用する。Zed における黄色の `nil` は 2 つの意味で孤立している。第一に、黄色を採用している実装が他に存在しないこと。第二に、Zed 独自のクエリは `nil` を `true`/`false` と分離しているが、公式 tree-sitter クエリはそのような分離を明確に否定し、`true`、`false`、`nil`、`iota` を同一の `@constant.builtin` キャプチャにまとめていることである。

JSON の真偽値はオレンジ色とする。One Dark Pro による言語別の例外設定を廃止し、TextMate-Atom および Zed との一致に復帰させた。これは後述の §9（2026-07 の一貫性監査）で発見・是正された。

## 3. 型

型ファミリーは黄色とし、黄色は型ファミリーのみに割り当てる。クラス、インターフェース、列挙型、名前空間、構造体、型パラメータを対象とし、Go の組み込みプリミティブ型（`int`、`string`、`error`）も含まれる。型が黄色になる理由は型だからであり、キーワード風の綴りであるかどうかは関係ない。Go のプリミティブ型は 2026-07 の一貫性監査（§9）まで紫色のままであった。

Zed における型のシアン配色は正当な系譜の 1 つであるが、本テーマでは採用しなかった。履歴の徹底的な調査により、以前の誤った見解が訂正された。シアンの型は base16 テンプレートの副産物ではなく、Tree-sitter 時代の Atom 自身が `type_identifier → support.storage.type` を通じて型をシアンで描画しており、Zed の 2023 年の手動調整はそれを意図的に継承したものだった。したがって黄色とシアンはいずれも異なる時代の Atom の正統な系譜である。本テーマのアーキテクチャ（TextMate 文法 + 言語サーバー）は TextMate 世代に属しており、エコシステム調査でも対象 8 実装すべてで型の黄色が一致していたため、黄色を維持する。

## 4. 変数、キー、パラメータ

変数ファミリーは赤色とし、`this` および `self` もこれに含める。これらは「値」であるため、設計哲学 §6（同一性の原則）に従い、固有の色ではなく通常の変数と同じ赤色を割り当てる。近年の tree-sitter オントロジーには `@variable.builtin` という区分が存在するが、同一性の原則を重視した。なお、`this` と `self` は 2026-07 の整理（§9）まで型の黄色になっていた。

ドットレシーバーおよびプロパティアクセスの中間プロパティは通常の変数として扱う。One Dark Pro は `variable.other.object` によってドットレシーバーを黄色に設定していたため、同一の変数であっても直後にドットが続くかどうかで色が変わってしまっていた。設計哲学 §6 の同一性の原則に基づきこれを廃止し、`a.b.c` における `b` も同様の決定に従う。One Dark Pro がこのルールで意図していたのは「コンテナ的な構造を黄色に見せること」であったが、それはセマンティックハイライトの namespace や class ルールによって正当に実現される。この変更に伴って生じる TextMate とセマンティックハイライトの差分は、`allow.json` の恒久的なエントリとして許容している。

キーファミリーはデータフォーマットを問わず赤色で統一する（JSON のキー、YAML のキー、CSS のプロパティ名、TOML の配列キー）。CSS のプロパティは Zed をリファレンスとしてファミリーの欠落を補完した。TOML の配列キーは One Dark Pro の名残で型の黄色になっていたが、セマンティックルールをファミリー名で記述するように移行した瞬間に不整合が顕在化した（"tomlArrayKey: type" と記述すれば誤りだと直感的に理解できるが、"#e5c07b" というカラーコードの直接指定では見落とされていた）。なお、ベンダープレフィックス付きの CSS プロパティ（`-webkit-*` など）は、プラットフォーム提供の要素としてシアンを維持する。

パラメータは赤色のイタリックとする。エコシステム調査の結果、これは One Dark Pro 固有の特徴であることが判明した（赤色自体は一般的だが、イタリック指定は稀である）。しかし本テーマでは意図してこれを維持しており、設計哲学 §7 に従い、歴史的由来ではなく視覚的アクセント（実用上の好み）として記録している。なお、Python 専用に設定されていたパラメータ固有色はファミリーの例外であったため、§9 の一貫性監査で削除した。

## 5. 埋め込み境界と文字列

`${}` および言語境界の記号類は暗赤色 `#BE5046` とする。TextMate-Atom における 78 件の定義を機械的に照合した上で原典に復帰させたものであり、原典、base16 の 0F スロット（"embedded language tags"）、および Atom に忠実な移植版すべて（akamud、joshdick、Sublime）で一致している。Tree-sitter 時代の Atom がこの色を失ったのは、エンジン移行時に波括弧のマッピングが欠落したためであり、意図的な設計変更ではなく移行時の脱落にすぎない。One Dark Pro は当初からこの色を持っていなかった。JSX 式の波括弧も同一スコープかつ「言語間の境界」という同一の意味を持つため、ワークベンチによる括弧の階層着色（Bracket Pair Colorization）の対象からあえて除外している。

`variable.interpolation` も暗赤色とし、同一ファミリーとして扱う。

正規表現はシアンとする。One Dark Pro における赤色は、issue #678 で VS Code Dark+ に寄せるために 2022 年に行われた意図的な改変であったが、設計哲学 §3 で述べたとおり Dark+ の模倣は本テーマの目標ではない。5 つのリファレンス間では 3 対 2 と僅差であり、近代的な世代では正規表現を「特殊な文字列」と解釈してオレンジ色を割り当てている。しかし、エコシステム調査において JetBrains、akamud、Sublime のすべてがシアンであることが確認されたため、シアンを採用して決着とした。

Markdown のリンク URL はシアンとする。`${}` と同様の照合により原典に復帰させた。

HTML エンティティはオレンジ色とする。理由の明記がない 2017 年の One Dark Pro の改変に対し、Atom と Zed が二世代にわたってオレンジ色で一致している。

CSS の単位はオレンジ色とする。One Dark Pro の赤色は 2018 年の外部 PR に由来し、その後のジェネレータ刷新で固定化されたものであり、原作者による設計意図すら伴っていなかった。

## 6. マークアップ

タグは赤色、属性はオレンジ色とする。リファレンスおよびエコシステム全体でほぼ完全に一致しており、base16 でも「XML Tags」を base08（赤）に分類している。Zed における青色のマークアップは Zed 独自の設計方針であり、付録に記載の廃止済み Zed バリアントにのみ残されていた。

見出し（Heading）は赤色とする。これは One Dark の正統な伝統であり、一部の派生テーマが使用しているシアンとは異なる。

## 7. シェル

コマンド名は緑色、`constant.other.option` に該当するフラグはシアン、クォートなしの引数は前景色（未着色）とし、ターミナルにおける zsh-syntax-highlighting の外観に揃えている。コマンド名の緑色は設計哲学 §2 で認めている 2 つの例外の 1 つであり、2026-07 の一貫性監査で再検討の上、有用性を認めて維持した。

## 8. ワークベンチ（UI 層）

シンボルアイコン等の配色は VS Code のデフォルトを維持する（2026-08-12 決定）。設計哲学 §3（非目標）に明記したとおり、UI 層のカスタマイズは視認性に重大な問題があるか著しく紛らわしい場合に限定し、トークンの語彙体系に揃えることだけを目的に変更することはない。VS Code のアイコンパレットは暗いワークベンチ上でも十分な視認性が確保されているため、たとえアイコンがトークンと同一の分類（クラス、関数など）を表している場合であっても、`symbolIcon.*` 等のキーは独自配色に変更していない。

同様の基準に基づき、`scmGraph` のカラーユニバーサルデザイン対応パレット、チャート表示、マージおよび diff の状態色もデフォルトのままとしている。

一方、Dark 2026 のアクセントカラー再着色はこの変更基準を満たしている。上流のティール（青緑）がシンタックスのシアン `#56B6C2` と衝突するため、13 色のアクセントファミリーを `#528BFF` に置き換えており、CI の色相帯スキャンによって整合性を防護している。

## 9. 過去に是正した判断ミス

プロジェクトの過程で誤った判断を下し、後に公に是正した事例を記録している。自らの決定を批判的に再検証することも本プロジェクトの設計プロセスの一部であるため、履歴として保持している。

2026-07 の一貫性監査では、テーマを自身の設計原則に照らして総点検した結果、自ら定めたルールに違反していた箇所が 5 件発見された。

1. TypeScript の型が黄色であるのに対し、Go のプリミティブ型が紫色になっていた → 黄色に修正（§3）。
2. `this` および `self` が型の黄色になっていた → 変数の赤色に修正（§4）。
3. Python のパラメータに言語固有の例外色が設定されていた → 赤色イタリックに統一（§4）。
4. JSON の真偽値に言語固有の例外色が設定されていた → オレンジ色に統一（§2）。
5. シェルのコマンド名が緑色になっていた → 検討の上、例外として維持（§7）。

その後、Dart 専用のセマンティック例外 4 件（いずれも One Dark Pro の名残）が、ルール記述をファミリー名ベースに移行したことで可視化され、削除された（Python のパラメータ是正と同等の判断）。この教訓として、フリッカー監査が検証する「レイヤー間の整合性」と「ファミリー体系としての一貫性」は別物であり、前者を満たしていても後者が破綻している場合があることが判明した。

その他の個別是正事項:

- 「Zed は LSP セマンティックハイライトに対応していない」: 古い情報であった。2026 年 2 月にオプトインで導入され、当時の Zed バリアントでは `"combined"` モードを再現した（付録参照）。
- 「型のシアンは base16 テンプレートの副産物である」: 部分的な誤認であった。Tree-sitter 時代の Atom による正統な系譜であることが判明した（§3）。
- 「One Dark Pro の正規表現の赤色は偶然の産物である」: VS Code Dark+ を意図的に模倣した変更であった。却下理由は「Dark+ の意図的な模倣」に修正されたが、結論（シアンの採用）に変更はない（§5）。
- 「Zed の正規表現のオレンジ色は他に類を見ない」: 近代的な tree-sitter オントロジーと一致する仕様であった。ただし本テーマにおけるシアンの採用はエコシステム調査等に基づく別個の根拠により維持している（§5）。
- 一時的に出荷した `function.defaultLibrary` をシアンにする「修正」: フリッカー検証ハーネスにより、フリッカーを解消するどころか逆に増加させることが実証されたため取り消した（設計哲学 §5）。
- 一時的に出荷した演算子をすべて前景色（未着色）にする案: 日常的な実使用において視認性に耐えられないことが判明し、即座に取り消した（§1）。
- 手動監査による組み込み色の誤判定、およびテーマコーパス照合による JetBrains の実属性キー `GO_LOCAL_VARIABLE` の見落とし: 目視や机上の知識ではなく、実エンジン（TextMate、LSP、ヘッドレス IDE）による機械的な検証システムを構築する契機となった（検証システムの詳細は README 参照）。

## 付録 Zed のエピソード: 検証ツールとしての忠実な再現

v0.0.x の一時期、本リポジトリでは Zed における One Dark の解釈を厳密に再現した 2 つのテーマを同梱していた。青いマークアップ、シアンの型、黄色の `nil` など、現在の決定で却下されている仕様も含めた再現であった。Zed のテーマスロットおよびセマンティックルール定義を機械的に変換し、Zed 自身の tree-sitter クエリによる実パース結果とトークン単位で照合・検証した（5,000 件以上のキャプチャで不一致ゼロ）。Zed 側で未定義の領域には「補完は行うがバグは持ち込まない」というルールを適用し、§9 の LSP 対応の是正後は Zed の `"combined"` モードを再現した。

このバリアントは v0.1.0 で廃止された。上記の決定で本バリアントを言及しているのは、双方の描画結果を直接比較することで「本テーマと Zed のどちらの配色が妥当か」という議論の多くに決着がついたためである。演算子、マークアップ、型ファミリーに関する論点の多くは、Zed の解釈環境を実際に構築・運用したことで浮き彫りになったものであった。
