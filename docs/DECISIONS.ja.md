# 決定

> English: [DECISIONS.md](DECISIONS.md)

議論のあった色の決定をトークンの族ごとに記録したもので、最後に後から直した
間違いをまとめてある。各項目はまず決定を書き、続けて根拠と経緯を書く。あとの
決定が前の決定を置き換えているものがいくつかあるので、分かる範囲で日付を残して
いる。

これらの決定の土台になっている原則は [PHILOSOPHY.ja.md](PHILOSOPHY.ja.md) に
あり、本文中の「哲学 §4」といった参照はそちらを指す。変更が新しい問題に決着を
付けたら、ここに書き足すこと。

## 1. 演算子

記号演算子はどの言語でもシアン `#56B6C2` にする。2026-07-20 の決定だ。演算子の族を分割
している参照元はひとつもなく、TextMate 時代の Atom は演算子を全部紫に、後期の
Atom は全部素の色に、Zed は全部シアンにしていて、base16 は演算子を base05、
つまり前景色に分類している。後のエコシステム調査でも、シアンは素・シアン・紫と
いう 3 つの有力な陣営のひとつで、akamud と One Dark Pro.nvim が同じだと分かった。
One Dark Pro が出荷していたのは混合で、論理演算子はシアン、三項とオプショナルは
単語演算子のグループ経由で紫、アローは紫、残りは素だった。この混合は出自の確認に
通らず、まとめて外した。最初に出荷したのは演算子を全部素の色にする案で、理屈の
うえでは正しかったのだが、同じ日に一目で取り消している。色の抜けた演算子は毎日
見るには耐えなかったので、代わりに Zed の全部シアンを採った。

`=>` は演算子として扱う。キーワードではない。これも 2026-07-20 の決定で、TextMate-Atom と One Dark
Pro の紫のアローが新しい参照元に負けた形になる。公式の tree-sitter クエリが `"=>"` を
他の記号と同じ `@operator` キャプチャに入れているからである。

単語演算子は紫のまま。`new`、`typeof`、`instanceof`、`in`、`of`、`delete`、
`void`、Python の `and/or/not` が対象で、単語はキーワード、記号は演算子と分け、
それぞれの族の中は一様にしておく。

型の世界の記号、つまり注釈の `:`、オプショナルの `?`、ユニオンの `|` は素の色の
まま。Zed はこれらを `punctuation.special` として暗赤に塗っているが、あれは Zed
独自の工夫なので取り込まなかった。

Go の演算子はひとつのシアンの族にする（`:=` `+` `*` `&` `&&` `==`）。One Dark
Pro には Go 特有の癖が 2 つあって、`:=` が黄なのは 2018 年の理由の書かれていない
コミットに、ポインタが紫なのは 2020 年のバグ報告へのパッチに由来する。どちらも
外した。後になって汎用の演算子の決定が Go の `&&` を素の色のまま取り残しそうに
なったので、`.go` スコープのエントリで族を保っている。

セマンティックの `operator` エントリは置かない。rust-analyzer などのサーバが
TextMate の言語ごとの演算子色を平らにならしてしまっていたので、哲学 §5 の
層構造の原則に従って削除した。

## 2. 定数とリテラル

名前付き定数はオレンジの値の族に統合した。これも 2026-07-20 である。`const` のローカル変数、
SCREAMING の定数、列挙メンバ、`Math.PI` や `JSON` のようなプラットフォーム定数は
すべて数値や真偽値と同じ `#D19A66` になり、この統合以降、黄が意味するものは型の
族だけになった。以前の黄への分割は One Dark Pro の特徴で族の他の系統にはなく、
エコシステムで分割している数少ないテーマもシアンや紫を使っているし、base16 は
定数とリテラルをまとめて base09 に入れている。統合した当初は
`variable.defaultLibrary` が黄のまま残っていたが、`JSON` に対する 3 件の新しい
ちらつき違反がそれを捕まえ、監査がリリース前に修正を強制した。原則の変更が、
一括修正で見落とされていたただひとつのルールを指し示したわけだ。

`nil`、`null`、`None` はリテラルなのでオレンジ。Zed の黄の `nil` は二重に孤立
していて、黄を使う実装は他にないし、Zed 自身のクエリは `nil` を `true` と
`false` から切り離しているのだが、公式の tree-sitter クエリはその分割をはっきり
否定して `true`、`false`、`nil`、`iota` をひとつの `@constant.builtin`
キャプチャにまとめている。

JSON の真偽値はオレンジ。One Dark Pro の言語別の例外をやめて TextMate-Atom と
Zed の一致に戻したもので、見つかったのは §9 の 2026-07 の一貫性整理のときで
ある。

## 3. 型

型の族は黄で、黄は型の族だけに使う。クラス、インターフェース、列挙型、名前空間、
構造体、型パラメータが対象で、Go の組み込みプリミティブ型 `int`、`string`、
`error` も含む。型が黄なのは型だからであって、綴りのせいではない。Go の
プリミティブ型は 2026-07 の整理（§9）まで紫だった。

Zed の型のシアンは正当な系譜だが、採用しなかった。ここは履歴を掘ったことで以前
の結論が覆ったところで、シアンの型は base16 テンプレートの副産物ではない。
Tree-sitter 時代の Atom 自身が `type_identifier → support.storage.type` を通じて
型をシアンで描画していて、Zed の 2023 年の手動調整はそれを意図的に残したのだから、
黄もシアンも時代の違う Atom の系譜である。このテーマのスタックは TextMate 文法に
言語サーバを重ねたもので TextMate 世代の子孫にあたり、エコシステム調査でも型の
黄は 8 実装すべてで一致していた。だから黄のままにする。

## 4. 変数、キー、パラメータ

変数の族は赤で、`this` と `self` も含む。あれは値なので、哲学 §6 のとおり専用の
色ではなく変数の赤にする。新しい tree-sitter のオントロジーには
`@variable.builtin` という区別があって、そこからの異議は記録に残してあるが、
それでも同一性の立場を取った。`this` と `self` は 2026-07 の整理（§9）まで型の
黄だった。

ドットレシーバとチェーン途中のプロパティは普通の変数である。One Dark Pro は
`variable.other.object` でドットレシーバを黄に塗るので、同じ変数でも後ろに
ドットが続くかどうかで色が変わってしまう。哲学 §6 の同一性の原則でこれを却下し、
`a.b.c` の `b` も同じ決定に従う。One Dark Pro があのルールで欲しかったのは
コンテナらしいものが黄に見えることで、それはセマンティックの namespace と
class のルールで正直に実現できる。この結果生じる TextMate とセマンティックの
食い違いは `allow.json` に恒久的なエントリとして置いてある。

キーの族はフォーマットをまたいで赤にする。JSON のキー、YAML のキー、CSS の
プロパティ名、TOML の配列キーが対象だ。CSS のエントリは Zed を参照元にして族の
穴を塞いだもので、TOML の配列キーは One Dark Pro の名残で型の黄になっていた。
セマンティックルールを族名で書くようにした瞬間にこれが表に出た。「tomlArrayKey:
type」と書いてあれば間違いだと分かるが、「#e5c07b」ではそうは読めなかった。
ベンダープレフィックス付きの CSS プロパティ（`-webkit-*` など）はシアンのまま
で、ベンダープレフィックスはプラットフォームが用意しているものとして扱う。

パラメータは赤のイタリック。エコシステム調査でこれは One Dark Pro の特徴だと
分かった。赤は一般的だが、イタリックはそうではない。承知のうえで残していて、
哲学 §7 のとおり出自ではなく好みとして記録している。Python 専用のパラメータ色は
族に対する例外だったので、§9 の整理のときに外した。

## 5. 埋め込みの境界と文字列

`${}` と埋め込みの句読点は暗赤 `#BE5046` にする。TextMate-Atom の 78 件の
割り当てをすべて機械的に照合したうえで起源に戻したもので、起源と、base16 の 0F
スロット「embedded language tags」と、Atom に忠実な移植のすべて（akamud、
joshdick、Sublime）が一致している。Tree-sitter 時代の Atom がこの色を失ったのは
移行時に波括弧の対応付けがなかったせいで、決定というより移行の損失にすぎない。
One Dark Pro はそもそもこの色を持っていなかった。JSX 式の波括弧も同じスコープで
同じ意味、つまり言語と言語の境目を持つので、ワークベンチの括弧の深さによる
色替えからはあえて外してある。

`variable.interpolation` も暗赤で、同じ族だ。

正規表現はシアン。One Dark Pro の赤は issue #678 で VS Code Dark+ に寄せた
2022 年の意図的な変更だったが、哲学 §3 にあるとおり Dark+ を真似ることはこの
テーマの目的ではない。5 つの参照元では 3 対 2 の僅差で、新しい世代は正規表現を
「特殊な文字列」と読んでオレンジにする。エコシステム調査で JetBrains、akamud、
Sublime のすべてがシアンだと分かって差が広がり、この問題は閉じた。

Markdown のリンク URL はシアン。`${}` と同じ照合で起源に戻したものだ。

HTML エンティティはオレンジ。説明のない 2017 年の One Dark Pro の編集に対し、
Atom と Zed が二世代にわたって一致している。

CSS の単位はオレンジ。One Dark Pro の赤をたどると 2018 年に外部から来た一括 PR
に行き着き、それをジェネレータの書き直しが焼き込んでいたのだから、作者自身の
設計ですらなかった。

## 6. マークアップ

タグは赤、属性はオレンジ。参照元でもエコシステムでもほぼ満場一致で、base16 も
「XML Tags」を base08 の赤に入れている。Zed の青いマークアップ族は Zed 独自の
設計方針で、付録に書いた廃止済みの Zed バリアントにだけ残っている。

見出しは赤。One Dark の伝統で、一部の派生が使うシアンとは違う。

## 7. シェル

コマンド名は緑、`constant.other.option` にあたるフラグはシアン、引用符なしの
引数は素の色で、zsh-syntax-highlighting に合わせたターミナルの見た目にしている。
この緑は哲学 §2 で認めている 2 つの例外のひとつで、2026-07 の整理で見直したうえ
で残した。

## 8. ワークベンチ（UI 層）

アイコンの色は VS Code のデフォルトのまま。2026-08-12 の決定。これはシンタックス
テーマなので、UI 層に手を入れるのはよほど見づらいか紛らわしいときだけで、
トークンの語彙と揃えるためだけには触らない。哲学 §3 にやらないこととして書いて
ある。VS Code のアイコンパレットは暗いワークベンチでも十分読めるので、
`symbolIcon.*` などのアイコンキーはテーマ化していない。アイコンがトークンと同じ
分類を描いているとしても、である。

同じ基準で、`scmGraph` の色覚多様性に配慮したパレット、チャート、マージと diff
の状態色もデフォルトのままにしてある。

2026 のアクセントの再対応はこの基準を満たしている。上流のティールがシンタックス
のシアン `#56B6C2` とぶつかるので、13 色のアクセント族を `#528BFF` に塗り替え、
哲学 §9 の色相帯スキャンがそれを守っている。

## 9. 後から直した間違い

このプロジェクトが間違え、後になって公開の場で直した結論を集めた。自分の決定を
見直すのも方法のうちなので、消さずに残している。

2026-07 の一貫性整理は、テーマを自分自身の原則に照らして監査したところから
始まり、自分のルールを破っている箇所が 5 つ見つかった。

1. TypeScript の型は黄なのに Go のプリミティブ型が紫だった。直した。§3。
2. `this` と `self` が型の黄になっていた。直した。§4。
3. Python のパラメータに言語別の例外色があった。直した。§4。
4. JSON の真偽値に言語別の例外色があった。直した。§2。
5. シェルのコマンド名が緑だった。見直したうえで残した。§7。

遅れて見つかったものがもうひとつある。Dart 専用のセマンティック例外が 4 件、
どれも One Dark Pro の名残で、族名で書くようにして見えるようになった時点で外した。
Python のパラメータと同じ判断だ。ここから得た教訓は、層の一貫性と族の一貫性は
別物だということで、ちらつき監査が調べるのは前者、前者を満たしていても後者は
壊れたままでありうる。

個別の訂正:

- 「Zed は LSP セマンティックハイライトに対応していない」。古い情報で、2026 年
  2 月にオプトインで入り、Zed バリアントは `"combined"` モードをモデル化した
  （付録）。
- 「型のシアンは base16 テンプレートの副産物」。半分間違いで、§3 に書いた
  とおり。
- 「One Dark Pro の正規表現の赤は偶然」。意図的な Dark+ の模倣だった。却下の
  理由は変わるが、結論は変わらない（§5）。
- 「Zed の正規表現のオレンジは他に例がない」。新しい tree-sitter のオントロジー
  と同じ側に立っているが、シアンの決定は別の根拠で維持する（§5）。
- `function.defaultLibrary` をシアンにする「修正」を短期間出荷し、ちらつき
  ハーネスがちらつきを減らすどころか増やしていることを示したので取り消した
  （哲学 §5 と §9）。
- 演算子を全部素の色にする案を短期間出荷し、毎日使ってみて間違いだと分かった
  ので取り消した。§1 の話である。

## 付録 Zed のエピソード: 計測器としての忠実さ

v0.0.x のある時期、このリポジトリは Zed の One Dark 解釈をそのまま再現した
テーマを 2 つ出荷していた。青いマークアップ、シアンの型、黄の `nil` といった、
上の決定が却下している部分まで含めてである。約束したのは忠実さであって判断ではなく、
Zed のテーマスロットとセマンティックルールのファイルを機械的に翻訳し、Zed 自身が
同梱するクエリで実際に tree-sitter パースした結果とトークン単位で突き合わせた
（5,000 を超えるキャプチャで不一致はゼロ）。Zed が決めていない部分は「隙間は
埋める、バグは埋めない」というルールで扱い、Zed がオプトインの LSP セマンティック
ハイライトに対応していると分かってからは Zed の `"combined"` モードをモデル化
した（§9）。

バリアントは v0.1.0 で廃止したが、このエピソードが原則を形作った。Zed の解釈の
中で暮らしてみたことで、上で決めた演算子、マークアップ、型の族の問題の大半が
浮かび上がったし、忠実な再現は計測器としても働いて、「うちの色と Zed の色、
どちらが正しいか」という議論のいくつかは両方の描画を並べたら決着した。Zed の
解釈が欲しい人は Zed で Zed のテーマを使えばいい。他のエディタの判断を再現するの
は研究の道具であって、製品ではない。
