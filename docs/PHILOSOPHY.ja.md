# 設計哲学

> English: [PHILOSOPHY.md](PHILOSOPHY.md)

このテーマがなぜその色でそのものを塗るのかを説明する文書で、テーマが何であるか、
各色が何を意味するか、そして色を決めるときの原則を扱う。個々の決定とその根拠や
経緯は [DECISIONS.ja.md](DECISIONS.ja.md) にまとめてあり、本文中の「決定 §3」と
いった参照はそちらを指している。ビルド・検証・保守の手順については英語の
[README](../README.md) を見てほしい。

One Dark Pro、TextMate、セマンティックトークン、base16、flicker といった用語は
末尾の用語集で説明する。

## 第 I 部 このテーマとは何か

### 1. 何がビルドされるか

ひとつのパイプラインから 2 つのテーマを作っていて、シンタックスの解釈は共通、
下に敷くワークベンチの世代だけが違う。

| テーマ | ワークベンチ |
|---|---|
| One Dark Modern | VS Code Dark Modern |
| One Dark 2026 | VS Code 2026 Dark（アクセントを `#528BFF` に再着色） |

背景色は必ずワークベンチ側の世代から取り、シンタックス層が背景色を決めることは
ない。

テーマは 3 つの要素の組み合わせである。シンタックス色はこのリポジトリ自身の
One Dark、UI は `#181818`/`#1F1F1F` の面と `#0078D4` のアクセントを持つ Dark
Modern、ターミナルのパレットは Atom の one-dark-ui にあった 16 色の ANSI セット
で、この組み合わせがコンセプトのすべてだ。

### 2. 色の語彙

色はそれぞれひとつの意味の族を表していて、色を見ただけでシンボルの種類が分かる
ようになっている。それがこのテーマの一番の価値なので、ある色を別の族にも
使い回すことは原則としてしない。使い回すたびに対応が少しずつ読みにくくなる。

以下の族は `syntax/families.json` にあるものそのままで、`syntax/tokens.json` と
`syntax/semantic.json` のルールはすべてこのどれかを名前で指し、それ以外の色は
ビルドが拒否する。つまりこの表は説明であると同時に、ビルドが実際に強制している語彙そのもの
でもある。

| 族 | 色 | 値 | 対象 |
|---|---|---|---|
| `keyword` | 紫 | `#C678DD` | 制御フロー、ストレージ、単語演算子（`func` `if` `const` `import` `new` `typeof` `and`） |
| `callable` | 青 | `#61AFEF` | 関数、メソッド、デコレータ、マクロ |
| `type` | 黄 | `#E5C07B` | 型の族だけ: クラス、インターフェース、列挙型、名前空間、構造体、型パラメータ |
| `variable-and-key` | 赤 | `#E06C75` | 変数の族（変数、フィールド、パラメータ、`this`/`self`）、キーに相当する名前（JSON/YAML のキー、CSS のプロパティ名）、マークアップのタグ、見出し |
| `platform-and-operator` | シアン | `#56B6C2` | プラットフォームが用意している名前（組み込み、エスケープ、正規表現、シェルのフラグ）と記号演算子（`=` `=>` `&&` `? :`） |
| `string` | 緑 | `#98C379` | 文字列、diff の追加行、シェルのコマンド名 |
| `value-constant` | オレンジ | `#D19A66` | 数値、真偽値、`nil`/`null`、名前付き定数、列挙メンバ、プラットフォーム定数（`Math.PI`）。属性名と太字マークアップもここ |
| `embedded-boundary` | 暗赤 | `#BE5046` | 言語と言語の境目: テンプレート内の `${}`、JSX 式の波括弧、`variable.interpolation` |
| `comment` | グレー | `#7F848E` | コメント（イタリック） |
| `comment-dim` | 薄いグレー | `#5C6370` | コメント内のリンク、Markdown の引用ブロック |
| `plain` | 前景色 | `#ABB2BF` | 句読点と型注釈の記号。ここはあえて色を付けない |
| `invalid` | エラー赤 | `#F44747` | 不正、壊れている、非推奨、未実装のトークン |

このほかに `style-only` という疑似族があって、色は持たずフォントスタイルだけを
担当する。パラメータのイタリック、JS/TS の属性のイタリック、Markdown の
イタリックと下線がこれにあたる。

族のルールには、承知のうえで認めている例外が 2 つある。ひとつはシェルのコマンド
名で、ターミナルの zsh-syntax-highlighting に合わせて文字列と同じ緑にしている。
決定 §7 に経緯がある。もうひとつは黄とオレンジの関係で、この 2 色は族というより「世界」
で分けている。黄は型の世界、オレンジは値の世界。型を指す名前なら Go の `int` や
`string` のような組み込みでも黄になるし、値を指す名前なら SCREAMING_CASE で
書かれていてもオレンジになる。経緯は決定 §2 と §3 にある。

#### 例

```ts
import { readFile } from "node:fs/promises";

export async function load(path: string, retries = MAX_RETRIES) {
  const text = await readFile(path);
  return `${text.length} bytes`;
}
```

| トークン | 族 |
|---|---|
| `import` `from` `export` `async` `function` `const` `await` `return` | `keyword`（紫） |
| `readFile` `load` | `callable`（青） |
| `"node:fs/promises"` とテンプレート文字列の本文 | `string`（緑） |
| `path`（パラメータ、イタリック）、`length` | `variable-and-key`（赤） |
| `string` | `type`（黄） |
| `MAX_RETRIES`、`text`（`const` のローカル変数は定数扱い。決定 §2） | `value-constant`（オレンジ） |
| `=` | `platform-and-operator`（シアン） |
| `${` `}` | `embedded-boundary`（暗赤） |
| `:` `{` `}` `(` `)` `,` `;` `.` | `plain`（前景色） |

### 3. やらないこと

- UI 層はデザインの対象にしない。よほど見づらいか紛らわしい箇所を除いて、Dark
  Modern や 2026 Dark のままにしておく。決定 §8 を参照。
- VS Code Dark+ や他のテーマを、それ自体を目的として真似ることはしない。決定 §5
  に一例がある。
- 他のエディタの解釈を再現したものは製品として出さない。研究の道具としては役に
  立つので Zed バリアントを作ったが、役目を終えた時点で廃止した。DECISIONS.ja.md
  の付録に経緯がある。
- プラットフォームの限界とは戦わない。あるプラットフォームで区別を表現できない
  ときは `audit/jetbrains-expected.json` に相違として書いておくだけにして、
  既知の例は README の JetBrains の節に載せている。

## 第 II 部 決め方

### 4. 出自: 色がどこから来たかで、その色の重みが決まる

受け継いだ色の重みはその履歴の分しかなく、「One Dark Pro にあったから」という
理由は、One Dark Pro がそれをどこから持ってきたかが分かった時点で通用しなく
なる。One Dark の実装はたくさんあって互いに食い違うが、食い違ったときは証拠で
決める。このテーマがたまたまどの実装の子孫かは関係ない。

#### 5 つの参照元

出自を確かめるときは、One Dark 族の 5 つの世代を見る。

1. TextMate 時代の Atom。2018 年より前の `atom/one-dark-syntax` で、これが
   起源になる。
2. Tree-sitter 時代の Atom。2018 年以降、同じチームがエンジンを載せ替えたもので、
   意図的に変えた色もあれば、文法スコープが消えたせいで失われた色もある。
3. base16。Kempson の 16 スロット標準と base16-onedark で、色の役割を文章で
   書き残している唯一の参照元である（たとえば「base09: Integers, Boolean,
   Constants, XML Attributes」）。だから「この色は何を意味するか」で揉めたとき
   の基準になるのだが、16 スロットしかなくて粗いし、書いたのは One Dark の作者
   ではない。
4. Zed。Atom チームが次に作ったエディタで、2022 年に base16 派生として始まり、
   2023 年に issue #5793 で Atom に寄せる手動調整が入った。本物の系譜に Zed
   独自の工夫がいくつか混じっている。
5. 公式の tree-sitter 文法クエリ。`audit/provenance/official-treesitter/` に
   スナップショットを置いてある。`=>` は演算子か、`nil` は `true` と同じ
   グループか、といった「どの区別が存在するか」については雄弁で、色については
   何も言わない。そしていつも正しいわけでもなく、語彙は文法ごとにばらつくし、
   SCREAMING ケースの名前を一律に `@constructor` とみなすような発見的規則も
   含んでいる。

#### 重み付けの仕方

多数決ではないが、頼りになると分かったパターンがいくつかある。

- ひとつの参照元にしかない逸脱は疑ってかかる。Zed の青いマークアップタグが
  そうだし、One Dark Pro が論理演算子だけシアンにしているのもそうだ。
- TextMate-Atom と Zed が一致していて One Dark Pro だけ違うなら、たいてい
  One Dark Pro の側がずれているので、そういう色は起源に戻した。
- 参照元が時代ごとにきれいに分かれるなら、どちらも正当な系譜である。型は
  TextMate 世代では黄、tree-sitter 世代ではシアンだったが、こういう場合は
  自分たちのスタックが属する世代に従う。
- どの参照元もやっていない分割は、どの参照元の立場よりも弱い。記号演算子を
  全部ひとつの色で塗るのは立場と言えるが、論理演算子だけを切り出すのは発明だ。

#### より広いエコシステム

5 つの参照元で差が僅差なら、もっと広いエコシステムを 6 番目の参照元として
参考にする。調べたのは JetBrains の one-dark プラグイン、akamud が Atom から
生成した VS Code 移植、joshdick・navarasu・olimorris の Vim/Neovim テーマ、
Sublime 移植、Emacs テーマ 2 つの、合わせて 8 つの実装。これで、ある立場が広い
合意なのか、族のある系統だけの特徴なのか、他に例のないものなのかが分かる。
決定を変えた知見は DECISIONS.ja.md に書いてある。調査ではもう 2 つ分かった
ことがあって、型の黄はエコシステム全体で満場一致だということと、`${}` の暗赤は
Atom に忠実な移植すべてが受け継いでいるということだ。

### 5. 層構造: 字句的なものは TextMate、セマンティックは訂正役

誤分類のしようがないもの、つまりキーワード、文字列、数値、コメント、演算子、
句読点は TextMate に任せる。正規表現で十分だし、TextMate は言語サーバが立ち上
がる前でも Markdown のコードフェンスの中でも動く。

誤分類されうるものはセマンティックトークンで直す。主な対象は識別子の役割で、
変数なのか、型なのか、関数なのかという問題だ。

だから、TextMate が意図して付けた色をセマンティックルールが塗り替えるのは
バグである。セマンティックルールにできるのは、TextMate が素の前景色のまま
残したトークンを埋めることと、TextMate 自身の推測が外れている箇所を直すことの
2 つだけで、それ以外はしない。

`npm run audit` が本物の文法と本物の言語サーバを使ってこれを機械的に強制する。
TextMate とセマンティックの食い違いは flicker（ちらつき）違反として報告され、
例外は `audit/allow.json` にしか置けず、ひとつひとつに理由が付く。

この原則から出た決定が 3 つある。セマンティックの `operator` エントリの削除
（決定 §1）、`function.defaultLibrary` の修正の取り消し（決定 §9）、そして
定数統合を完成させたちらつき違反（決定 §2）だ。

### 6. 同一性: 同じシンボルには同じ色

色はシンボルが何であるかに付くもので、どこに書かれているかには付かない。

決定的な事例が One Dark Pro のドットレシーバの黄で、あのルールだと同じ変数なのに
後ろにドットが続くかどうかで色が変わってしまう。これは却下した。`this` と
`self` も同じ原則で決まっていて、あれは値なので専用の色ではなく変数の赤にする。
どちらも決定 §4 にある。

§7 の上流に対する実用主義とぶつかったら、こちらが勝つ。

### 7. 上流に対する実用主義

`atom/one-dark-syntax` からの忠実な再構築は一度やってみて、やめた。灰色の
パラメータ、前景色の演算子、暗いコメントは毎日使うには耐えなかった。One Dark
Pro の 150 ほどの言語別ルールは実際の文法に対する 10 年分の調整で、これは大きな
財産である。ただし One Dark Pro は従うべき権威ではなく審査する依存関係であって、
個々のルールは出自の確認で履歴の弱いものが見つかるまでの間だけ有効だった。
最初は基準で、次にルールごとに審査する依存関係になり、今は複数ある参照元の
ひとつにすぎない。v0.1.0 以降はその変更を同期しておらず、取り込む価値のある
ものは他の参照元と同じ道、つまり決定を経て入ってくる。

好みの判断では、この系統のテーマを何年も毎日使って慣らした目を物差しにする。
その結果が 2 つあって、どちらも正直に書いておく。まず、One Dark Pro の特徴を
2 つ、純粋に好みで残している。パラメータのイタリック（決定 §4）と、証拠に
よって退けられるまで長く残していた定数の黄（決定 §2）だ。それから、机上では
正しいスキームを見た目の理由で却下したことが一度ある。決定 §1 の、演算子を
すべて素の色にする案である。履歴が色を提案し、毎日の使用が最終的に決める。

### 8. 決定は理由付きで書き残す

色の理由は機械可読な場所に置き、チャットのログやコミットメッセージには置か
ない。

- `audit/allow.json` には、セマンティックが TextMate を上書きしてよい場所と
  その理由がある。
- `audit/jetbrains-expected.json` には、実際の IDE で保証する色と、文書化した
  相違がある。
- `DECISIONS.md` には、議論のあった決定とその根拠・経緯がある。
- この文書には原則がある。

この 4 つを合わせたものがこれまでの決定の記録で、何かを変えるときはまずこの
記録と照らし合わせる。変更が新しい問題に決着を付けたなら、DECISIONS.md に
書き足す。

### 9. 仮定するな、計測せよ

色は本物のエンジンに対して検証し、知識や対応表やコーパスは当てにしない。

- VS Code は `vscode-textmate` に gopls と typescript-language-server を組み
  合わせて、`npm run audit` で確認する。
- JetBrains は GoLand と WebStorm をヘッドレスで動かし、実際のトークン属性
  キーをフォールバックチェーンごとにダンプする（`jetbrains-audit/`）。
- 2026 のアクセントは、色相帯スキャンが 13 色のアクセント族の再対応を守って
  いる。

なぜこうするかは、このリポジトリの履歴が示している。慎重にやった手動監査が
組み込みの色を誤判定し、テーマコーパスとの照合は本当のキー `GO_LOCAL_VARIABLE`
を見落とした。もっともらしいセマンティックの「修正」は出荷前にハーネスが反証
したし、原則の変更が 3 件のちらつき違反を引き起こして、その違反が一括修正で
見落とされていたただひとつのルールを指し示したこともある。どちらも決定の §9 と
§2 に書いた。一度起きた種類のバグには、必ず機械的な守りを付ける。

検証にどれだけ手間をかけるかは、テーマとピクセルの間にどれだけの知能が挟まって
いるかで決める。一番手厚いのが IntelliJ、次に VS Code、その次が Vim で、
ターミナルは受動的なパレットなので生成が正しいかどうかを見れば済む。

## 用語集

- One Dark Pro: このリポジトリが言語ルールを吸収し、その後ルールごとに審査した
  VS Code テーマ（§7）。
- TextMate: VS Code が字句ハイライトに使う正規表現ベースの文法層。言語サーバが
  なくても動く、というのが §5 の話の前提になる。
- セマンティックトークン、LSP: 変数・型・関数といった役割の情報。言語サーバが
  供給し、TextMate の上に重なる（§5）。
- Flicker（ちらつき）: TextMate の色とセマンティックの色が食い違うトークン。
  言語サーバが起動した瞬間に目に見えて色が変わるもので、`npm run audit` の
  層構造検査はこれを単位に数える（§5）。
- base16: Kempson の 16 スロット配色標準。スロットの役割が文書化されているので、
  意味で揉めたときの基準になる（§4）。
- 参照元: §4 で出自を確かめるときに見る、One Dark の 5 つの世代のひとつ。
- 族: `syntax/families.json` で名前を付けた意味のグループで、色はこの単位で
  割り当てる（§2）。
- `allow.json`: §8 で触れた、認めた TextMate とセマンティックの食い違いの
  一覧。それぞれに理由が付く。
- Dark+、Dark Modern、2026 Dark: VS Code 標準のダークテーマ。Dark Modern と
  2026 Dark はこのテーマのワークベンチ UI を供給し、Dark+ はかつて One Dark Pro
  が真似した相手として出てくるだけ（決定 §5）。
- ワークベンチ: VS Code の UI クローム（サイドバー、タブ、ターミナルなど）で、
  エディタのシンタックス色と対になる言葉（§1、決定 §8）。
