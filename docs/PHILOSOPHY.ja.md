# 設計哲学

> English: [PHILOSOPHY.md](PHILOSOPHY.md)

このドキュメントは、前提知識のない読者に向けて、このテーマがなぜその色でその
ものを塗るのかを説明する。リポジトリ内のあらゆる色の決定はこのドキュメントから
導出可能であるべきで、新しい疑問が生じたときは、答えを発明する前にここの裁定を
確認すること。

構成は 4 部からなる:

- **第 I 部 — このテーマとは何か**（§1–2）: アイデンティティと色の語彙。
- **第 II 部 — 決め方**（§3–8）: あらゆる裁定の論拠となる原則。
- **第 III 部 — 裁定**（§9–17）: 争点となった決定の完全な記録をトークン族ごとに
  まとめたもの。訂正の記録を含む。
- **第 IV 部 — 構成と運用**（§18–21）: 色がどこに住み、どう生成・検証され、
  リポジトリがどう保守されるか。

付録は 2 つ: Zed のエピソード（A）と用語集（B）。全体で使う略語 — ODP、TM、
LSP、base16、flicker（ちらつき）— は用語集で定義する。

---

## 第 I 部 — このテーマとは何か

### 1. アイデンティティ

ひとつのパイプラインから 2 つのテーマがビルドされる。ひとつのシンタックス解釈
を、2 世代のワークベンチに載せたものだ。

| テーマ | ワークベンチ |
|---|---|
| One Dark Modern | VS Code Dark Modern |
| One Dark 2026 | VS Code 2026 Dark（アクセントを `#528BFF` に再着色） |

背景色は常にワークベンチ世代に由来し、シンタックス層からは決して来ない。

アイデンティティの配合は次のとおり: このリポジトリ自身の One Dark シンタックス
色、Dark Modern の UI（`#181818`/`#1F1F1F`、アクセント `#0078D4`）、そして Atom
one-dark-ui の 16 色 ANSI ターミナルパレット。この三者の配合こそがコンセプト
*そのもの*である。

（Zed の One Dark 解釈をそのまま再現した 2 テーマが v0.0.x の間に出荷され、
v0.1.0 で廃止された。付録 A を参照。）

### 2. 色の語彙

各色は**意味の族**に対応する。シンボルの種類をその色から読み取れることがこの
テーマの核心的価値であり、ある色を別の族のために借用することは対応を薄めるため、
原則として禁止される。

以下の族は `syntax/families.json` にあるものそのままである。`syntax/tokens.json`
と `syntax/semantic.json` のすべてのルールはこのいずれかを名前で参照し、ビルドは
それ以外の色を拒否する（§19）。したがってこの表は単なる文書ではなく、実行可能な
語彙である。

| 族 | 色 | 値 | 対象 |
|---|---|---|---|
| `keyword` | 紫 | `#C678DD` | 制御フロー、ストレージ、単語演算子（`func` `if` `const` `import` `new` `typeof` `and`） |
| `callable` | 青 | `#61AFEF` | 関数、メソッド、デコレータ、マクロ |
| `type` | 黄 | `#E5C07B` | 型の族、そしてそれ以外は何もない: クラス、インターフェース、列挙型、名前空間、構造体、型パラメータ |
| `variable-and-key` | 赤 | `#E06C75` | 変数の族（変数、フィールド、パラメータ、`this`/`self`）、キー的な名前（JSON/YAML キー、CSS プロパティ名）、マークアップタグ、見出し |
| `platform-and-operator` | シアン | `#56B6C2` | プラットフォーム提供の魔法（組み込み、エスケープ、正規表現、シェルフラグ）と記号演算子（`=` `=>` `&&` `? :`） |
| `string` | 緑 | `#98C379` | 文字列、diff の追加行、シェルのコマンド名 |
| `value-constant` | オレンジ | `#D19A66` | 数値、真偽値、`nil`/`null`、名前付き定数、列挙メンバ、プラットフォーム定数（`Math.PI`）。加えて属性名と太字マークアップ |
| `embedded-boundary` | 暗赤 | `#BE5046` | 世界と世界の境界: テンプレート内の `${}`、JSX 式の波括弧、`variable.interpolation` |
| `comment` | グレー | `#7F848E` | コメント（イタリック） |
| `comment-dim` | 薄いグレー | `#5C6370` | コメント内のリンク、Markdown の引用ブロック |
| `plain` | 前景色 | `#ABB2BF` | 句読点、型注釈の記号 — 「あえてハイライトしない」という意図的な選択 |
| `invalid` | エラー赤 | `#F44747` | 不正、壊れた、非推奨、未実装のトークン |

疑似族 `style-only` は色を持たず、フォントスタイルだけを担う（パラメータの
イタリック、JS/TS 属性のイタリック、Markdown のイタリックと下線）。

意図的な不純物が 2 つ、正典として認められている:

- シェルのコマンド名は緑（文字列の色）。ターミナルの zsh-syntax-highlighting
  を映したものである（§15）。
- 黄/オレンジは厳格な二世界分割をなす: **黄は型の世界、オレンジは値の世界。**
  型を名指すシンボルは、たとえ組み込みでも（Go の `int`、`string`）黄であり、
  値を名指すシンボルは、たとえ SCREAMING_CASE でもオレンジである（§10、§11）。

## 第 II 部 — 決め方

### 3. 出自: 色の権威はその歴史にある

中心教義: **継承された色の権威は、その出自にある。** 歴史が判明した後は、
「One Dark Pro にあったから」というだけでは理由にならない。One Dark には互いに
食い違う多くの実装が存在する。食い違ったとき、決着をつけるのは証拠であって、
このテーマがたまたまどの実装の子孫であるかではない。

#### 5 人の証人

出自スコアリングは One Dark 族の 5 つの地層を認める:

1. **TextMate 時代の Atom**（2018 年以前の `atom/one-dark-syntax`）— 起源。
2. **Tree-sitter 時代の Atom**（2018 年以降）— エンジン移行後の同じチーム。
   意図的に変更された色もあれば、翻訳の過程で失われた色（もはや存在しなくなった
   文法スコープ）もある。
3. **base16**（Kempson の 16 スロット標準、および base16-onedark）— *役割を文書
   として*記録している唯一の証人（「base09: Integers, Boolean, Constants, XML
   Attributes」）。そのため「どの色が何を意味するか」の論争における公式辞書と
   なるが、粗く（16 スロット）、One Dark の原作者によるものではない。
4. **Zed** — Atom チームの後継エディタ。base16 工場として始まり（2022 年）、
   2023 年に Atom への忠実さに向けて手動調整された（issue #5793）。本物の血統と、
   Zed 独自の孤立した発明の両方を抱える。
5. **公式 tree-sitter 文法クエリ**（`audit/provenance/official-treesitter/` に
   スナップショット）— *どの区別が存在するか*（`=>` は演算子か？ `nil` は `true`
   と同じグループか？）については重みがあり、色については沈黙し、無謬でもない。
   語彙は文法ごとにばらつきがあり、SCREAMING ケースを `@constructor` とする
   ような発見的規則を正典化している。

#### 証人の重み付け

スコアリングは機械的な多数決ではない。観察された規則性:

- いずれか単一の証人による孤立した逸脱は疑わしい（Zed の青いマークアップタグ、
  ODP の論理演算子シアンの特別扱い）。
- ODP に対する二世代の一致（TextMate-Atom ＋ Zed）は、通常 ODP がドリフトした
  ことを意味する。そうした色は起源へ復元された。
- 証人が時代によってきれいに分かれる場合（型: TextMate 地層では黄、tree-sitter
  地層ではシアン）、どちらの立場も正当な血統である。テーマは自身のスタックが
  由来する地層に従う。
- *どの証人も行っていない分割*は、どの証人の立場よりも弱い。すべての記号演算子
  をひとつの色で塗るスキームは「立場」だが、論理演算子だけを残りから分割する
  スキームは「発明」である。

#### エコシステムによる確認

5 人の証人で差が僅差にとどまる場合、より広いエコシステムが 6 番目の助言的な
情報源となる。さらに 8 つの実装（JetBrains の one-dark プラグイン、akamud の
Atom 生成 VS Code 移植、joshdick/navarasu/olimorris の Vim/Neovim テーマ、
Sublime 移植、2 つの Emacs テーマ）を調査し、ある立場が広範な合意なのか、族の
特徴なのか、孤児なのかを検出する。裁定を変えた知見は第 III 部に記録されている。
調査はまた、型＝黄がエコシステム全体で満場一致であること、`${}` の暗赤が
Atom に忠実なすべての移植に受け継がれていることも確認した。

### 4. 層構造: 字句的なものは TextMate に属し、セマンティックは訂正する

- **誤分類されえないもの**（キーワード、文字列、数値、コメント、演算子、
  句読点）は TextMate に属する。そこでは正規表現で十分であり、TM は LSP が
  起動する前も Markdown のコードフェンス内でも動作し続ける。
- **誤分類されうるもの**（識別子の役割: 変数か？ 型か？ 関数か？）はセマンティック
  トークンによって訂正される。
- したがって: **TextMate が意図的に設定した色をセマンティックルールが塗り替える
  ことは違反である。** セマンティックが許されるのは、TM が素の前景色のまま
  残したトークンを埋めること、または TM 自身の推測が間違っている箇所を直す
  ことだけである。
- `npm run audit`（本物の文法 ＋ 本物の LSP）がこれを機械的に強制する。
  TM とセマンティックの不一致は *flicker*（ちらつき）違反である。例外は
  `audit/allow.json` にのみ存在し、それぞれに理由が付いている。

この原則から導かれた裁定: セマンティックの `operator` エントリの削除（§9）、
取り消された `function.defaultLibrary` の修正（§17）、定数統合を完成させた
ちらつき違反（§10）。

### 5. 同一性: 同じシンボルには同じ色

色はシンボルが**何であるか**に付随するのであって、**どこに書かれているか**には
付随しない。

決定的な事例は One Dark Pro の黄いドットレシーバで、同じ変数がドットの前に
あるかどうかで色が変わる。これは却下された（§12）。この原則は `this`/`self` の
裁定の根拠でもある: これらは値なので、特別な色ではなく変数の赤を纏う（§12）。

この原則は、衝突した場合に上流への忠実さ（§6）より優先する。

### 6. 上流への実用主義（純粋主義なし）

`atom/one-dark-syntax` からの忠実な再構築は一度試みられ、却下された: グレーの
パラメータ、前景色の演算子、暗いコメントは日常使用に耐えなかった。One Dark Pro
の約 150 の言語別ルールは、実際の文法に対する 10 年の調整の成果 — 価値はあるが、
**ODP は審査対象の依存関係であって正典ではない**。そのルールは、出自審査が弱い
血統のものを見つけるまでのみ有効だった（§3、第 III 部）。こうして ODP は降格の
弧を完了した: 正典 → 審査対象の依存関係 → 参考資料。v0.1.0 以降、ODP の変更は
同期されない（§19）。取り込む価値のあるものは、他のどの証人の立場とも同じ道 —
裁定 — を通って到着する。

好みの判断の物差しは、この血統を長年日常的に使ってきたことで校正された目である。
2 つの帰結を正直に記録する: このテーマは好みとして 2 つの ODP の特徴を保って
いる（パラメータのイタリック、§12。そして証拠が退けるまで長らく受け継いでいた
定数＝黄の特徴、§10）。また、教義的には正しいスキーム（オール素の演算子、§9）
を、実際に見て間違って見えたという理由で一度却下した。**出自が提案し、日常使用
が裁く。**

### 7. 決定はデータである

色の背後にある *なぜ* は、チャットログやコミットメッセージではなく、理由付きの
機械可読な場所に住む:

- `audit/allow.json` — セマンティックが TM を上書きしてよい場所と、その理由
- `audit/jetbrains-expected.json` — 実際の IDE で保証される色と、文書化された
  相違
- このドキュメント — 原則と裁定

これらが合わさって判例記録をなす。変更はまず判例に照らして確認すべきである。

### 8. 仮定するな、計測せよ

色は知識、対応表、コーパスではなく、**本物のエンジン**に対して検証される:

- VS Code: `vscode-textmate` ＋ gopls / typescript-language-server
  （`npm run audit`）
- JetBrains: ヘッドレスの GoLand / WebStorm が、実際のトークン属性キーを
  フォールバックチェーンごとにダンプする（`jetbrains-audit/`）
- 2026 アクセント: 色相帯スキャンが 13 色のアクセント族の再対応を守る

仮定が外れることを示す、このリポジトリの歴史からの証拠: 慎重な手動監査が
組み込みの色を誤判定した。テーマコーパスによる確認が本当のキー
`GO_LOCAL_VARIABLE` を見落とした。もっともらしいセマンティックの「修正」が、
出荷前にハーネスによって反証された（§17）。教義の変更が 3 件のちらつき違反を
引き起こし、それが一掃で見落とされたただひとつのルールの位置を特定した（§10）。
**一度起きたバグの類型には、すべて機械的な守りを付ける。**

検証への投資は、**テーマとピクセルの間にどれだけの知能が挟まっているか**に
比例させる: IntelliJ > VS Code > Vim > ターミナル（受動的なパレット。生成の
正しさ以外に確認すべきものはない）。

## 第 III 部 — 裁定

争点となった決定の完全な記録を、トークン族ごとにまとめる。各項目はまず**裁定**
を述べ、次にその根拠と経緯を述べる。いくつかの裁定は以前の裁定を上書きするため、
判明している日付は残している。

### 9. 演算子

**記号演算子はすべての言語でシアン `#56B6C2`**（2026-07-20）。

- *根拠:* 演算子の族を分割する証人はいない。TextMate 時代の Atom はすべての
  演算子を紫にした。後期 Atom はすべて素のままにした。Zed はすべてシアンにする。
  base16 は演算子を base05（前景色）に分類する。後のエコシステム調査で、シアンは
  3 つの有力な陣営（素/シアン/紫）のひとつであり、akamud と One Dark Pro.nvim
  と共有されていることが示された。
- *経緯:* ODP は混合を出荷した（論理演算子はシアン、三項/オプショナルは単語
  演算子グループ経由で紫、アローは紫、残りは素）。この混合は出自審査に落ち、
  一掃された。教義的に純粋なオール素の救済策が先に出荷されたが、同日に一目で
  覆された。洗い流されたような演算子は「共に暮らす」テストに落ち、代わりに
  Zed のオールシアンの立場が採用された。

**`=>` はキーワードではなく演算子**（2026-07-20）。紫のアロー（TextMate-Atom ＋
ODP）は現代の証人に敗れた。公式 tree-sitter は `"=>"` を他のすべての記号と同じ
`@operator` キャプチャに列挙している。

**単語演算子は紫のまま**: `new`、`typeof`、`instanceof`、`in`、`of`、`delete`、
`void`、Python の `and/or/not`。単語はキーワード、記号は演算子。各族は内部で
一様である。

**型世界の記号は素のまま**: 注釈の `:`、オプショナルの `?`、ユニオンの `|`。
Zed はこれらを暗赤（`punctuation.special`）に塗るが、これは Zed 単独の発明で
あり、取り込まない。

**Go の演算子はひとつのシアンの族**（`:=` `+` `*` `&` `&&` `==`）。ODP の Go の
癖（2018 年の理由なきコミットによる `:=` の黄、2020 年のバグ報告パッチによる
ポインタの紫）は捨てられた。後に汎用の演算子裁定が Go の `&&` を素のまま
取り残しかけたとき、`.go` スコープのエントリが族を保った。

**セマンティックの `operator` エントリは持たない。** rust-analyzer などの
サーバが TM の言語ごとの演算子色を平坦化していたため、層構造の原則（§4）の
もとでエントリは削除された。

### 10. 定数とリテラル

**名前付き定数はオレンジの値の族に統合**（2026-07-20）: `const` ローカル、
SCREAMING 定数、列挙メンバ、プラットフォーム定数（`Math.PI`、`JSON`）はすべて
数値や真偽値と同じ `#D19A66` を纏う。この統合以後、黄が意味するのはただひとつ、
型の族である。

- *根拠:* 以前の黄への分割は、他のどの One Dark 族も共有しない ODP 血統の特徴
  だった（エコシステムで分割する数少ない実装はシアンや紫を使う）。base16 は
  定数とリテラルをまとめて base09 に分類する。
- *経緯:* 統合は当初 `variable.defaultLibrary` を黄のまま取り残していた。
  `JSON` に対する 3 件の新しいちらつき違反がそれを捕捉し、監査がリリース前に
  修正を強制した — 教義の変更が、一掃で見落とされたただひとつのルールの位置を
  特定した。

**`nil`/`null`/`None` はオレンジ** — これらはリテラルである。Zed の黄い `nil`
は二重に孤立している: 黄を使う実装は他になく、Zed 自身のクエリは `nil` を
`true`/`false` から分割している — 公式 tree-sitter クエリが明示的に否定する
分割である（`true`/`false`/`nil`/`iota` をひとつの `@constant.builtin`
キャプチャにまとめている）。

**JSON の真偽値はオレンジ** — ODP の言語別例外に対して、TextMate-Atom ＋ Zed の
一致を復元（2026-07 の自己一貫性粛清で発見、§17）。

### 11. 型

**型の族は黄であり、黄は型の族だけである。** クラス、インターフェース、
列挙型、名前空間、構造体、型パラメータ — Go の組み込みプリミティブ型
（`int`、`string`、`error`）を含む: 型が黄なのは型だからであって、綴り方の
せいではない。（Go のプリミティブ型は 2026-07 の粛清まで紫だった、§17。）

**Zed の型シアンは正当な血統だが、採用しない。** 深い考古学が以前の判定を
訂正した: シアンの型は base16 工場の産物ではない — tree-sitter 時代の Atom
自身が型をシアンで描画しており（`type_identifier → support.storage.type`）、
Zed の 2023 年の手動調整は意図的にそれを保った。黄もシアンも、異なる時代の
Atom の祖先である。このテーマのスタック（TextMate 文法 ＋ LSP）は TextMate
地層の子孫であり、エコシステム調査でも型＝黄が 8 実装すべてで満場一致だった
ため、黄が維持される。

### 12. 変数、キー、パラメータ

**変数の族は赤**、`this`/`self` を含む。これらは値なので、特別な色ではなく
変数の赤を纏う（§5）。現代の tree-sitter オントロジーからの異議（区別として
`@variable.builtin` が存在する）は記録に残っており、同一性の族の観点から
退けられている。（2026-07 の粛清まで型の黄を纏っていた、§17。）

**ドットレシーバとチェーン途中のプロパティは普通の変数。** One Dark Pro は
ドットのレシーバを黄に塗る（`variable.other.object`）ため、同じ変数がドットの
前にあるかどうかで色が変わる。これは同一性の原則（§5）のもとで却下された。
`a.b.c` の `b` も同じ裁定に服する。ODP がこのルールで望んだもの —「コンテナ的
なものが黄に見える」— は、セマンティックの namespace/class ルールによって
正直に達成される。対応する TM↔セマンティックの不一致は `allow.json` の恒久的
エントリである。

**キーの族はフォーマットを横断して赤**: JSON キー、YAML キー、CSS プロパティ名
（CSS のエントリは Zed を証人として族の穴を塞いだ）、TOML の配列キー（ODP の
残滓が型の黄に塗っていた。セマンティックルールが族名で書かれるようになった
瞬間にこの化石は浮上した — 「tomlArrayKey: type」は、「#e5c07b」では決して
そう読めなかった形で、間違いとして読める）。ベンダープレフィックス付きの
CSS プロパティ（`-webkit-*`）はシアンのまま: ベンダープレフィックスは
プラットフォームの魔法である。

**パラメータは赤のイタリック。** エコシステム調査はこれを ODP の特徴として
切り出した（赤は一般的だが、イタリックはそうではない）。特徴として意図的に
維持 — 出自ではなく好みとして記録（§6）。Python 専用のパラメータ色は族に
対する例外であり、2026-07 に粛清された（§17）。

### 13. 埋め込み境界と文字列

**`${}` と埋め込みの句読点は暗赤 `#BE5046`** — TextMate-Atom の全 78 割り当て
を機械的に照合した後、起源へ復元された。

- *根拠:* 起源 ＋ base16 の 0F スロット（「embedded language tags」）＋ Atom に
  忠実なすべての移植（akamud、joshdick、Sublime）が一致する。
- *経緯:* tree-sitter 時代の Atom はこの色を*失った*（移行時に波括弧の対応付けが
  なかった — 決定ではなく翻訳の損失）。ODP は一度も持たなかった。
- JSX 式の波括弧も同じスコープと同じ意味を持つ: 世界と世界の境界であり、
  ワークベンチの括弧深度サイクルから意図的に除外されている。

**`variable.interpolation` は暗赤** — 同じ族。

**正規表現はシアン。** ODP の赤は VS Code Dark+ を模倣した 2022 年の意図的な
変更だった（issue #678）— Dark+ の模倣はこのテーマの原則ではない。5 人の証人
のスコアは僅差の 3 対 2 だった（現代の地層は正規表現を「特殊な文字列」、
つまりオレンジと読む）。エコシステム調査（JetBrains、akamud、Sublime がすべて
シアン）が差を広げ、問題を閉じた。

**Markdown のリンク URL はシアン**（起源の復元、`${}` と同じ照合による）。

**HTML エンティティはオレンジ**（説明のない 2017 年の ODP 編集に対して、
Atom ＋ Zed の二世代一致）。

**CSS の単位はオレンジ**（ODP の赤は 2018 年の外部からの一括 PR に遡り、
ジェネレータの書き直しで焼き込まれた — 作者自身の設計ですらない）。

### 14. マークアップ

**タグは赤、属性はオレンジ** — 証人とエコシステムでほぼ満場一致（base16 は
「XML Tags」を base08 の赤に分類する）。Zed の青いマークアップ族は孤立した
哲学の軸であり、廃止された Zed バリアントにのみ残された（付録 A）。

**見出しは赤**（One Dark の伝統。一部の派生が使うシアンではない）。

### 15. シェル

**コマンド名は緑、フラグ（`constant.other.option`）はシアン、引用符なしの引数は
素のまま** — zsh-syntax-highlighting に合わせた、ターミナル校正済みの見た目。
この緑は正典化された 2 つの不純物のひとつであり（§2）、2026-07 の粛清で審査の
うえ維持された。

### 16. ワークベンチ（UI 層）

**アイコンの色は VS Code のデフォルトのまま**（2026-08-12）。これはシンタックス
テーマである: UI 層に手を入れるのは何かが本当に見づらいか紛らわしいときだけで、
トークン語彙との一貫性のためだけには決して触らない。VS Code のアイコン
パレットは暗いワークベンチ上で判読可能なので、`symbolIcon.*` や他のアイコン
キーはテーマ化しない — アイコンがトークンと同じ分類を描画しているとしても。

**同じ基準により `scmGraph` の色覚多様性に配慮したパレット、チャート、マージ/
diff の状態色もデフォルトのままである。**

**2026 のアクセント再対応はこの基準を満たす**: 上流のティールがシンタックスの
シアン `#56B6C2` と衝突するため、13 色のアクセント族を `#528BFF` に再着色する
（色相帯スキャンが守る、§8）。

### 17. 訂正の記録

このプロジェクトが間違え、後に公開の場で修正した判定 — 自分自身の裁定を
再検証することは方法論の一部なので、ここに残す。

**自己一貫性の粛清（2026-07）。** このドキュメントそのものに対してテーマを
監査したところ、5 件の自己違反が見つかった:

1. TS の型は黄なのに Go のプリミティブ型が紫 — 修正（§11）。
2. `this`/`self` が型の黄を纏う — 修正（§12）。
3. Python パラメータの言語別例外色 — 修正（§12）。
4. JSON 真偽値の言語別例外色 — 修正（§10）。
5. シェルのコマンド名が緑 — 審査のうえ維持（§15）。

遅れて響いた余波: Dart 専用の 4 件のセマンティック例外（ODP の残滓）は、族名に
よる命名で可視化されたことで粛清された — Python パラメータの粛清と同じ判断で
ある。教訓: 層の一貫性（ちらつき監査が検査するもの）は族の一貫性ではない —
前者は、後者の違反を正典化したままでも満たせてしまう。

**個別の訂正:**

- 「Zed は LSP セマンティックハイライトをサポートしていない」— 古い情報。
  2026 年 2 月にオプトインで実装された。Zed バリアントは `"combined"` モードを
  モデル化した（付録 A）。
- 「型シアンは base16 テンプレートの産物」— 半分間違い。§11 を参照。
- 「ODP の正規表現の赤は偶然」— 意図的な Dark+ の模倣だった。却下の理由は
  変わるが、結果は変わらない（§13）。
- 「Zed の正規表現オレンジは孤児」— 現代の tree-sitter オントロジーの側に立って
  いる。シアンの裁定は別の根拠で維持される（§13）。
- `function.defaultLibrary` のシアン「修正」は短期間出荷され、取り消された:
  ちらつきハーネスが、それがちらつきを取り除くどころか*導入する*ことを示した
  （§4、§8）。
- オール素の演算子スキームは短期間出荷され、日常使用が反証したため取り消された
  （§9）。

## 第 IV 部 — 構成と運用

### 18. 唯一の真実の源、あらゆる場所へ生成

**ビルドされた VS Code テーマ（`themes/*.json`）が、すべてのプラットフォームに
とっての唯一の真実の源である。** JetBrains の `.icls`、Ghostty、Windows
Terminal、Vim の成果物は One Dark 2026 から生成される（`scripts/lib.ts`、
`loadBuiltTheme`）ため、16 進値の一致は構造的に保証される。これらは
「One Dark Modern」というスキーム名を保つ。これは拡張機能のアイデンティティ
であって、バリアントのラベルではない。

- 生成ファイル（`themes/`、`dist/`）は決して手で編集しない。CI が再現性を
  検証する。
- 手で編集する唯一の面は `syntax/`、`overrides/`、そして `audit/` 配下の判断
  記録である。

### 19. シンタックス層は所有し、UI 層は差分をとる

**シンタックスには上流がない。** v0.1.0 以降、`syntax/` はこのリポジトリ自身の
真実の源である。`families.json` は §2 の語彙を 16 進値に対応付け、`tokens.json`
と `semantic.json` のルールは族を名前で参照する。したがって色はちょうどひとつの
場所に存在し、ビルドは語彙の外の色を持つルールやセマンティックエントリを
拒否する。

**どう同梱されたか。** ルールはビルド済みテーマから同梱された — バイト単位で
同一の出力、機械検証済み — One Dark Pro の 10 年の文法調整が完全に吸収され、
争点となったルールのすべてが出自プロセス（§3、§6、第 III 部）で承認または
廃棄された後のことである。続く v0.1.1 のリファクタリングは、同じ族のルールを
統合し、死んだ重複を削除することで、同梱ルールを 288 から 14 に圧縮した。各
ステップは本物の TextMate エンジンに対して検証済み: 6,762 のフィクスチャ
トークンと 464 のセレクタすべてで同一の解決。

**UI 層は差分である。** `overrides/` は Dark Modern / 2026 Dark に対する UI 層の
差分だけを保持する。これらは引き続き生きた上流である。エントリを残すかどうかの
テストは: *「これを削除したら、テーマのコンセプトは損なわれるか？」* 損なわれ
ないなら上流に委ねる — オーバーライドが小さいほど、週次の自動同期の見返りは
大きい。

### 20. プラットフォームの語彙の限界を受け入れる

プラットフォームが表現できない区別は、戦うのではなく相違として文書化する
（`audit/jetbrains-expected.json`）:

- IntelliJ には TS 向けの const/readonly キーがない → そこでは const は赤のまま
- PyCharm にはパラメータ専用のキーがない → `DEFAULT_PARAMETER`（赤のイタリック）
  が代役を務める
- Pylance はクローズドソース → Python のセマンティック層は自動検証の外側
  （目視でカバー）

### 21. 運用

- **上流の同期。** UI の上流（Dark Modern、2026 Dark）は CI にゲートされた PR を
  通じて週次で同期し、その PR は自身でマージしリリースする。シンタックスには
  上流がなく、同期で変わることは決してない。同期を止めるには、その PR を閉じる。
- **保守ループ。** (a) 不一致をスクリーンショットし、(b) `syntax/` または
  `overrides/` を調整し、(c) 裁定を第 III 部に記録する。
- **リリース。** 手動リリースは `npm version patch` — どちらにせよ 5 つの
  プラットフォーム成果物が自動的に出荷される。

## 付録 A. Zed のエピソード: 計測器としての忠実さ

v0.0.x の一時期、このリポジトリは Zed の One Dark 解釈をそのまま再現した 2 つの
テーマも出荷していた — このドキュメントの裁定が却下する部分（青いマークアップ、
シアンの型、黄の `nil`）も含めて。その契約は**判断ではなく忠実さ**だった: Zed の
テーマスロットとセマンティックルールファイルの機械的翻訳を、Zed 自身が同梱する
クエリを使った実際の tree-sitter パースに対してトークン単位で検証し（5,000 以上の
キャプチャ、不一致ゼロ）、Zed が未指定のまま残した部分には「隙間埋めは可、
バグは不可」のルールを適用した。Zed がオプトインの LSP セマンティックハイライト
をサポートすることが判明してからは、Zed の `"combined"` モードをモデル化した
（§17）。

バリアントは v0.1.0 で廃止されたが、このエピソードは教義を形作った: Zed の
解釈の中で暮らすことで、第 III 部で裁定された演算子、マークアップ、型の族の
問題の大半が浮上し、忠実な再現は計測器として機能した — 「我々の色と Zed の色、
どちらが正しいか」という論争のいくつかは、両方の描画を並べることで決着した。
Zed の解釈が欲しい人は Zed で Zed のテーマを使えばよい。他のエディタの判断を
再現することは研究の道具であって、製品ではない。

## 付録 B. 用語集

- **ODP** — One Dark Pro。このリポジトリがその言語ルールを吸収し、その後ルール
  ごとに審査した VS Code テーマ（§6）。
- **TM / TextMate** — VS Code が字句ハイライトに使う正規表現ベースの文法層。
  言語サーバなしで動作する（§4）。
- **セマンティックトークン / LSP** — 言語サーバが供給する役割情報（変数、型、
  関数）。TM の上に重ねられる（§4）。
- **Flicker（ちらつき）** — TM の色とセマンティックの色が食い違うトークン。
  言語サーバが起動すると目に見えて色が変わる。`npm run audit` の層構造検査の
  単位（§4）。
- **base16** — Kempson の 16 スロット配色標準。スロットの役割が文書化されて
  いるため、意味の論争における公式辞書となる（§3）。
- **証人** — 出自スコアリングで参照する One Dark の 5 つの地層のひとつ（§3）。
- **族** — `syntax/families.json` に名前で定義された意味のグループ。色を割り
  当てる単位（§2）。
- **`allow.json`** — 容認された TM↔セマンティックの不一致の一覧。それぞれに
  理由が付く（§7）。
- **Dark+ / Dark Modern / 2026 Dark** — VS Code 自身のデフォルトのダークテーマ。
  Dark Modern と 2026 Dark はこのテーマのワークベンチ UI を供給し、Dark+ は
  かつて ODP が模倣した対象としてのみ関係する（§13）。
- **ワークベンチ** — VS Code の UI クローム（サイドバー、タブ、ターミナル）。
  エディタのシンタックス色と対をなす（§1、§16）。
