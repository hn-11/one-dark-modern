# 設計哲学

> English: [PHILOSOPHY.md](PHILOSOPHY.md)

本書は、本テーマにおける配色の根拠と方針をまとめた設計ドキュメントである。テーマの基本構成、各色の意味定義、および配色選定の原則について解説する。個別の配色決定の経緯や根拠については [DECISIONS.ja.md](DECISIONS.ja.md)（本文中では「決定 §3」のように参照）にまとめている。ビルド・検証・保守手順については [README](../README.md)（英語）を参照されたい。

なお、One Dark Pro、TextMate、セマンティックトークン、base16、フリッカー（flicker）などの用語定義は末尾の用語集に記載している。

## 第 I 部 本テーマの構成と設計思想

### 1. 生成されるテーマ

単一のビルドパイプラインから 2 つのテーマバリアントを生成している。シンタックスハイライトの定義は共通であり、ベースとなるワークベンチUIの世代のみが異なる。

| テーマ | ワークベンチ |
|---|---|
| One Dark Modern | VS Code Dark Modern |
| One Dark 2026 | VS Code Dark 2026（アクセントを `#528BFF` に再着色） |

背景色は常にワークベンチ側の定義をそのまま継承し、シンタックス層が背景色を変更することはない。

本テーマは以下の 3 つの要素で構成される。独自にチューニングした One Dark シンタックス配色、`#181818`/`#1F1F1F` のサーフェスと `#0078D4` のアクセントを持つ Dark Modern UI、そして Atom の one-dark-ui 由来の 16 色 ANSI ターミナルパレットである。この組み合わせが本テーマの基本コンセプトである。

### 2. カラーパレットの語彙体系（ファミリー）

各色はそれぞれ特定の意味カテゴリ（ファミリー）に対応しており、色を見るだけでシンボルの役割を判別できるように設計されている。これは本テーマの中核的な価値であるため、1つの色を複数のファミリーで安易に流用することは原則として避けている。流用が増えるほど、色とシンボル種別の対応関係が曖昧になるためである。

以下のファミリー定義は `syntax/families.json` の内容と完全に一致している。`syntax/tokens.json` および `syntax/semantic.json` のハイライトルールはすべてこれらのファミリー名を指定して記述されており、語彙外の直接的な色指定はビルド時にエラーとしてはじかれる。したがって、この表は単なる説明用資料ではなく、ビルドシステムによって機械的に強制される仕様そのものである。

| ファミリー | 色 | カラーコード | 主な対象 |
|---|---|---|---|
| `keyword` | 紫 | `#C678DD` | 制御構文、宣言修飾子、キーワード演算子（`func` `if` `const` `import` `new` `typeof` `and` など） |
| `callable` | 青 | `#61AFEF` | 関数、メソッド、デコレータ、マクロ |
| `type` | 黄 | `#E5C07B` | 型定義全般: クラス、インターフェース、列挙型、名前空間、構造体、型パラメータ |
| `variable-and-key` | 赤 | `#E06C75` | 変数全般（ローカル変数、フィールド、パラメータ、`this`/`self`）、キー相当の識別子（JSON/YAML のキー、CSS プロパティ名）、マークアップのタグ名、見出し |
| `platform-and-operator` | シアン | `#56B6C2` | プラットフォーム標準の識別子（組み込み定数/関数、エスケープ文字、正規表現、シェルフラグ）および記号演算子（`=` `=>` `&&` `? :`） |
| `string` | 緑 | `#98C379` | 文字列リテラル、diff の追加行、シェルコマンド名 |
| `value-constant` | オレンジ | `#D19A66` | 数値リテラル、真偽値、`nil`/`null`、名前付き定数、列挙メンバ、プラットフォーム標準定数（`Math.PI` など）。属性名や太字マークアップも含む |
| `embedded-boundary` | 暗赤 | `#BE5046` | 言語間の境界構文: テンプレート文字列内の `${}`、JSX 埋め込み式の波括弧、`variable.interpolation` |
| `comment` | グレー | `#7F848E` | コメント（イタリック） |
| `comment-dim` | 薄いグレー | `#5C6370` | コメント内のリンク、Markdown の引用ブロック |
| `plain` | 前景色 | `#ABB2BF` | 句読点、記号、型注釈の記号（あえてハイライトしない要素） |
| `invalid` | エラー赤 | `#F44747` | 構文エラー、破損、非推奨、未実装のトークン |

このほかに、色を持たずフォントスタイルのみを適用する疑似ファミリー `style-only` が存在する。パラメータのイタリック、JS/TS 属性のイタリック、Markdown のイタリックおよび下線がこれに該当する。

ファミリーの規則には、設計上意図して設けている例外が 2 点ある。
1つはシェルコマンド名で、ターミナルにおける zsh-syntax-highlighting の慣例に合わせて文字列と同じ緑色を採用している（経緯は決定 §7 参照）。
もう1つは黄色とオレンジ色の関係で、これらは単なるファミリーの区別にとどまらず、「型（Type）」と「値（Value）」という2つの領域の境界として切り分けている。黄色は型、オレンジ色は値を表す。したがって、型を表す識別子であれば Go の `int` や `string` のような組み込みプリミティブであっても黄色となり、値を表す識別子であれば SCREAMING_SNAKE_CASE であってもオレンジ色となる（経緯は決定 §2 および §3 参照）。

#### ハイライト例

```ts
import { readFile } from "node:fs/promises";

const MAX_RETRIES = 3;

export async function load(path: string, retries = MAX_RETRIES) {
  const text = await readFile(path);
  return `${text.length} bytes`;
}
```

| トークン | 適用ファミリー |
|---|---|
| `import` `from` `export` `async` `function` `const` `await` `return` | `keyword`（紫） |
| `readFile` `load` | `callable`（青） |
| `"node:fs/promises"` およびテンプレート文字列のテキスト | `string`（緑） |
| `path`、`retries`（パラメータ: イタリック）、`length` | `variable-and-key`（赤） |
| `string` | `type`（黄） |
| `3`、`MAX_RETRIES`、`text`（`const` ローカル変数は定数扱い。決定 §2 参照） | `value-constant`（オレンジ） |
| `=` | `platform-and-operator`（シアン） |
| `${` `}` | `embedded-boundary`（暗赤） |
| `:` `{` `}` `(` `)` `,` `;` `.` | `plain`（前景色） |

上記は TypeScript 言語サーバー（LSP）が稼働している場合の色分けである。TextMate 単体では、ドット直前の `text` や import 文内の `readFile` は異なる色で描画されるが、この差分はセマンティックハイライトによる正当な補正として許容している（決定 §4 参照）。

### 3. 非目標（スコープ外とすること）

- **UI 層を独自に再設計しない**: 視認性に重大な問題がある場合や紛らわしい箇所を除き、Dark Modern および Dark 2026 の上流スタイルをそのまま維持する（決定 §8 参照）。
- **他のテーマを目的なく模倣しない**: VS Code Dark+ やその他のテーマを、それ自体を目的に追従・模倣することはしない（決定 §5 参照）。
- **他エディタの再現バリアントを製品として提供し続けない**: 検証・研究ツールとしては有用であったため一時的に Zed バリアントを提供していたが、役目を終えた段階で廃止した（詳細は [DECISIONS.ja.md](DECISIONS.ja.md) の付録を参照）。
- **プラットフォーム固有の限界に抗わない**: 特定のプラットフォームで構文の区別を表現できない場合は、無理に対処せず `audit/jetbrains-expected.json` に仕様差として記録するにとどめる（既知の事例は README の JetBrains セクションを参照）。

## 第 II 部 配色の判断原則

### 4. 由来（プロベナンス）: 配色の根拠とその重み付け

継承された配色の正当性はその歴史的経緯に依存する。「One Dark Pro に存在した」という事実は、One Dark Pro 自身がどこからその色を取り入れたのかが判明した時点で根拠としての有効性を失う。One Dark には多数の実装が存在し、相互に差異がある。方針が分かれた際は、本テーマがどの実装から派生したかではなく、客観的な証拠に基づいて判断する。

#### 5 つのリファレンス

配色の由来を検証する際、One Dark の系譜における 5 つの世代・情報源を参照する。

1. **TextMate 時代の Atom**: 2018 年以前の `atom/one-dark-syntax`。これが One Dark の原典となる。
2. **Tree-sitter 時代の Atom**: 2018 年以降、同一チームによって構文エンジンが刷新された世代。意図的に変更された配色もあるが、文法スコープの廃止に伴って失われた配色も存在する。
3. **base16**: Chris Kempson による 16 色スロット規格と、それに基づく base16-onedark。色の役割が文書として明記されている唯一の情報源である（例:「base09: Integers, Boolean, Constants, XML Attributes」）。色の意味付けに関する議論で重要な基準となるが、16 スロットと粒度が粗く、One Dark の原作者自身による記述ではない点に留意する必要がある。
4. **Zed**: Atom 開発チームが新たに開発したエディタ。2022 年に base16 派生として始まり、2023 年（issue #5793）に Atom の再現性を高める手動調整が行われた。原典の系譜を引き継ぎつつも、Zed 独自の設計判断が一部に含まれる。
5. **公式 tree-sitter 文法ハイライトクエリ**: `audit/provenance/official-treesitter/` にスナップショットを保存している。「`=>` は演算子か」「`nil` は `true` と同グループか」といった構文上の分類基準を客観的に示すが、色自体については規定しない。また、文法定義ごとに語彙のばらつきがあり、SCREAMING_CASE の識別子を一律に `@constructor` とみなすようなヒューリスティクスを含むなど、常に万全とは限らない。

#### 証拠の評価基準

単純な多数決ではないが、検証を通じて確立された判断基準がある。

- **単一のリファレンスにしか存在しない逸脱は疑う**: Zed の青いマークアップタグや、One Dark Pro による論理演算子のみのシアン化などが該当する。
- **TextMate-Atom と Zed が一致し、One Dark Pro のみ異なる場合は原典を優先する**: 多くの場合 One Dark Pro 側の独自の差異であるため、原典の定義に復帰させる。
- **世代によって評価が分かれる場合は、本テーマの構文スタックが属する世代に準拠する**: 例えば型定義の色は TextMate 世代では黄色、tree-sitter 世代ではシアンであった。このような場合は、本テーマのアーキテクチャ（TextMate + LSP）が属する世代の方針に従う。
- **いずれのリファレンスも行っていない独自の分割は採用しない**: 記号演算子すべてを1つの色で統一するのは正当な方針だが、論理演算子だけを勝手に切り出して別色にするのは根拠のない独自改変とみなす。

#### エコシステム全体の調査

上記 5 つのリファレンスで判断が拮抗した場合は、エコシステム全体の動向を第6の参考情報とする。具体的には、JetBrains の one-dark プラグイン、Atom から直接生成された akamud 版 VS Code 移植、Vim/Neovim 向け（joshdick、navarasu、olimorris）、Sublime Text 移植、Emacs 向け（2種）の計 8 実装を調査した。これにより、特定の方針が広範なコンセンサスに基づくものか、特定系統の固有仕様か、あるいは孤立した例外かが明確になる。この調査によって下された決定は [DECISIONS.ja.md](DECISIONS.ja.md) に記録している。なお、この調査を通じて「型の黄色」はエコシステム全体で完全に一致していること、また「`${}` の暗赤色」は Atom に忠実なすべての移植版で一貫して引き継がれていることが確認された。

### 5. レイヤリング: 字句ハイライトは TextMate、セマンティックは補正

構文解析のみで誤判別の余地がないトークン（キーワード、文字列、数値、コメント、演算子、句読点）は TextMate に委ねる。これらは正規表現で十分に判定可能であり、言語サーバーが起動する前や、Markdown 内のコードブロック内でも即座に正しく機能する。

字句解析だけでは判別が難しいトークン（主に識別子が変数・型・関数のいずれであるか）については、セマンティックトークンによって補正する。

したがって、TextMate が意図して割り当てた色を、セマンティックルールが無用に上書き再着色することは設計上のバグとみなす。セマンティックルールの役割は、TextMate が未装飾の前景色のまま残したトークンに着色すること、および TextMate による誤推測を訂正することの 2 点に限定される。

README で説明しているフリッカー監査（flicker audit）は、実際の文法定義と実言語サーバーを用いてこの整合性を機械的に検証する。意図的に許容する例外については `audit/allow.json` に明記し、個別に理由を記録している。

この原則に基づいて行われた決定として、セマンティックの `operator` エントリの削除（決定 §1）、`function.defaultLibrary` に対する安易な修正の取り消し（決定 §9）、および定数統合の契機となったフリッカー違反の是正（決定 §2）の 3 件がある。

### 6. シンボルの同一性: 同一のシンボルには同一の色を割り当てる

色はシンボル自体の本質に対して割り当てられるべきであり、コード上の出現位置によって変動してはならない。

代表例が One Dark Pro におけるドットレシーバーの黄色ハイライトである。このルールでは、同一の変数であっても直後にドットが続くかどうかで色が変わってしまう。本テーマでは同一性の原則に基づきこれを明確に却下した。`this` や `self` の扱いも同様であり、これらは値であるため、専用色ではなく通常の変数と同じ赤色を割り当てる（いずれも決定 §4 参照）。

本原則（同一性）が §7 のプラグマティズムと競合した場合は、本原則を優先する。

### 7. 上流（One Dark Pro / Atom）に対するプラグマティズム

`atom/one-dark-syntax` の完全な忠実再現は、初期に試みたものの採用を見送った。パラメータの灰色、演算子の前景色（無着色）、極端に暗いコメントなどは、日常的な開発環境における視認性に耐えうるものではなかったためである。One Dark Pro が持つ約 150 の言語別ルールは、実際の文法定義に対する 10 年におよぶ調整の蓄積であり、極めて有用な資産である。しかし One Dark Pro は絶対的な基準ではなく、ルール単位で精査すべき対象である。各ルールは由来の正当性が確認できる間のみ維持され、根拠の薄いものは順次見直された。当初は参照の起点であったが、ルールごとの精査対象となり、現在では複数あるリファレンスの 1 つに位置づけられている。採用に値する変更は、他のリファレンスと同様に検証プロセス（決定の記録）を経て取り込まれる。

視覚的な好みが関わる判断においては、この系統のテーマを長年使用してきた実体験を評価基準としている。その結果として以下の 2 点が挙げられる。
第 1 に、One Dark Pro の特徴的な配色のうち 2 点を視認性の観点からあえて維持している。パラメータのイタリック指定（決定 §4）と、証拠に基づいて見直されるまで長期間維持していた定数の黄色（決定 §2）である。
第 2 に、理論上は正統とされながらも、実際の視覚的フィードバックに基づいて却下した例がある。決定 §1 で触れている「演算子をすべて前景色（無着色）にする」方針である。歴史的な経緯が色の候補を提示し、実際の使用感が最終的な採否を決定する。

## 用語集

- **One Dark Pro**: 本リポジトリが言語ルールのベースとして取り込み、その後ルール単位で精査を行った VS Code テーマ（§7）。
- **TextMate**: VS Code が字句ハイライトに使用する正規表現ベースの文法解析エンジン。言語サーバーが未起動でも高速に動作する（§5）。
- **セマンティックトークン / LSP**: 言語サーバー（Language Server）から提供される識別子の意味情報（変数、型、関数など）。TextMate レイヤーの上に重なって適用される（§5）。
- **Flicker（フリッカー / 表示のちらつき）**: TextMate による着色と言語サーバーによるセマンティック着色の間で色が食い違う現象。言語サーバーの解析完了時にトークンの色が突然切り替わる不自然な描画を指す。`npm run audit` ではこの発生件数を機械的に検査する（§5）。
- **base16**: Chris Kempson による 16 色のスロット配色規格。各スロットの意味的な役割が文書化されており、配色の妥当性を検証する際の客観的な基準となる（§4）。
- **リファレンス（情報源）**: §4 において配色の由来を検証する際に参照する、One Dark の 5 つの世代・情報源。
- **ファミリー（Family）**: `syntax/families.json` で定義されている意味的なトークン分類。配色はすべてこのファミリー単位で割り当てられる（§2）。
- **`allow.json`**: TextMate とセマンティックハイライトの間で意図的に許容された色差分の一覧。全件に正当化理由が記録されている（§5）。
- **Dark+、Dark Modern、Dark 2026**: VS Code 標準のダークテーマ。Dark Modern および Dark 2026 は本テーマのワークベンチ UI のベースとして使用されている。Dark+ はかつて One Dark Pro が模倣の対象としていた旧標準テーマ（決定 §5）。
- **ワークベンチ**: VS Code のエディタ周辺 UI（サイドバー、ステータスバー、タブ、統合ターミナルなど）。エディタ内のシンタックスハイライトと対比される概念（§1、決定 §8）。
