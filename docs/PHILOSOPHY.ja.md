# 設計哲学

> English: [PHILOSOPHY.md](PHILOSOPHY.md)

このドキュメントは、このテーマがなぜその色でそのものを塗るのかを説明する。
リポジトリ内のあらゆる色の決定はここから導出できるべきで、新しい疑問が出てきた
ときは、答えを考え出す前にここに記録された決定を確認する。

構成は 4 部からなる:

- 第 I 部 — このテーマとは何か（§1–2）: アイデンティティと色の語彙。
- 第 II 部 — 決め方（§3–8）: すべての決定の論拠になる原則。
- 第 III 部 — 決定（§9–17）: 議論のあった決定をトークン族ごとに記録したもの
  と、私たちが訂正した間違い。
- 第 IV 部 — 構成と運用（§18–21）: 色がどこにあり、どう生成・検証され、
  リポジトリがどう保守されるか。

付録は 2 つ: Zed のエピソード（A）と用語集（B）。全体で使う用語 — One Dark Pro、
TextMate、セマンティックトークン、base16、flicker（ちらつき）— は用語集で
定義する。

---

## 第 I 部 — このテーマとは何か

### 1. アイデンティティ

ひとつのパイプラインから 2 つのテーマがビルドされる。ひとつのシンタックス解釈
を、2 世代のワークベンチに載せたものだ。

| テーマ | ワークベンチ |
|---|---|
| One Dark Modern | VS Code Dark Modern |
| One Dark 2026 | VS Code 2026 Dark（アクセントを `#528BFF` に再着色） |

背景色は常にワークベンチ世代に由来し、シンタックス層からは来ない。

このテーマは 3 つのものの組み合わせである: このリポジトリ自身の One Dark
シンタックス色、Dark Modern の UI（`#181818`/`#1F1F1F`、アクセント `#0078D4`）、
そして Atom one-dark-ui の 16 色 ANSI ターミナルパレット。この組み合わせが
コンセプトである。

（Zed の One Dark 解釈をそのまま再現した 2 テーマが v0.0.x の間に出荷され、
v0.1.0 で廃止された。付録 A を参照。）

### 2. 色の語彙

各色はひとつの意味の族を表す。シンボルの種類を色から読み取れることがこの
テーマの主な価値なので、ある色を別の族に借用することは原則として認めない。
対応が薄まるからだ。

以下の族は `syntax/families.json` にあるものそのままである。`syntax/tokens.json`
と `syntax/semantic.json` のすべてのルールはこのいずれかを名前で参照し、ビルドは
それ以外の色を拒否する（§19）。したがってこの表は単なる文書ではなく、実行可能な
語彙である。

| 族 | 色 | 値 | 対象 |
|---|---|---|---|
| `keyword` | 紫 | `#C678DD` | 制御フロー、ストレージ、単語演算子（`func` `if` `const` `import` `new` `typeof` `and`） |
| `callable` | 青 | `#61AFEF` | 関数、メソッド、デコレータ、マクロ |
| `type` | 黄 | `#E5C07B` | 型の族、そしてそれ以外は何もない: クラス、インターフェース、列挙型、名前空間、構造体、型パラメータ |
| `variable-and-key` | 赤 | `#E06C75` | 変数の族（変数、フィールド、パラメータ、`this`/`self`）、キー的な名前（JSON/YAML キー、CSS プロパティ名）、マークアップタグ、見出し |
| `platform-and-operator` | シアン | `#56B6C2` | プラットフォームが提供する名前（組み込み、エスケープ、正規表現、シェルフラグ）と記号演算子（`=` `=>` `&&` `? :`） |
| `string` | 緑 | `#98C379` | 文字列、diff の追加行、シェルのコマンド名 |
| `value-constant` | オレンジ | `#D19A66` | 数値、真偽値、`nil`/`null`、名前付き定数、列挙メンバ、プラットフォーム定数（`Math.PI`）。加えて属性名と太字マークアップ |
| `embedded-boundary` | 暗赤 | `#BE5046` | 言語と言語の境界: テンプレート内の `${}`、JSX 式の波括弧、`variable.interpolation` |
| `comment` | グレー | `#7F848E` | コメント（イタリック） |
| `comment-dim` | 薄いグレー | `#5C6370` | コメント内のリンク、Markdown の引用ブロック |
| `plain` | 前景色 | `#ABB2BF` | 句読点、型注釈の記号 — 「あえてハイライトしない」という意図的な選択 |
| `invalid` | エラー赤 | `#F44747` | 不正、壊れた、非推奨、未実装のトークン |

疑似族 `style-only` は色を持たず、フォントスタイルだけを担う（パラメータの
イタリック、JS/TS 属性のイタリック、Markdown のイタリックと下線）。

族のルールに対する例外を 2 つ、意図的に認めている:

- シェルのコマンド名は緑（文字列の色）。ターミナルの zsh-syntax-highlighting
  に合わせるため（§15）。
- 黄とオレンジは厳密に二つの世界に分かれる: 黄は型の世界、オレンジは値の世界。
  型を名指すシンボルは、たとえ組み込みでも（Go の `int`、`string`）黄であり、
  値を名指すシンボルは、たとえ SCREAMING_CASE でもオレンジである（§10、§11）。

## 第 II 部 — 決め方

### 3. 出自: 色がどこから来たかで、その色の重みが決まる

受け継いだ色の重みは、その履歴の分しかない。「One Dark Pro にあったから」は、
履歴が分かった時点で理由ではなくなる。One Dark には互いに食い違う多くの実装が
あり、食い違ったときは、このテーマがたまたまどの実装の子孫かではなく、証拠で
決着をつける。

#### 5 つの参照元

出自の確認では、One Dark 族の 5 つの世代を参照する:

1. TextMate 時代の Atom（2018 年以前の `atom/one-dark-syntax`）— 起源。
2. Tree-sitter 時代の Atom（2018 年以降）— エンジン移行後の同じチーム。
   意図的に変えた色もあれば、文法スコープがなくなったために移行で失われた色
   もある。
3. base16（Kempson の 16 スロット標準、および base16-onedark）— 色の役割を
   文書として書き残している唯一の参照元（「base09: Integers, Boolean,
   Constants, XML Attributes」）。そのため「この色は何を意味するか」の議論では
   基準になるが、粗く（16 スロット）、One Dark の作者が書いたものではない。
4. Zed — Atom チームがその後作ったエディタ。base16 派生として始まり（2022 年）、
   2023 年に Atom に近づける手動調整を受けた（issue #5793）。本物の系譜と、
   Zed 独自の工夫がいくつか混じっている。
5. 公式 tree-sitter 文法クエリ（`audit/provenance/official-treesitter/` に
   スナップショット）。どの区別が存在するか（`=>` は演算子か？ `nil` は `true`
   と同じグループか？）については多くを語り、色については何も語らず、常に
   正しいわけでもない。語彙は文法ごとにばらつきがあり、SCREAMING ケースの
   名前を `@constructor` とみなすような発見的規則を含んでいる。

#### 重み付けの仕方

多数決ではない。信頼できると分かったパターン:

- ひとつの参照元にしかない逸脱は疑わしい（Zed の青いマークアップタグ、
  One Dark Pro の論理演算子だけシアンにする特別扱い）。
- TextMate-Atom と Zed が One Dark Pro に対して一致するとき、たいてい
  One Dark Pro のほうがずれている。そうした色は起源に戻した。
- 参照元が時代ではっきり分かれる場合（型: TextMate 世代では黄、tree-sitter
  世代ではシアン）、どちらも正当な系譜であり、自分たちのスタックが由来する
  世代に従う。
- どの参照元も行っていない分割は、どの参照元の立場よりも弱い。すべての記号
  演算子をひとつの色で塗るのは「立場」だが、論理演算子だけを残りから分けるのは
  「発明」である。

#### より広いエコシステム

5 つの参照元で差が僅差にとどまるときは、より広いエコシステムも助言的な 6 番目の
参照元として見る。さらに 8 つの実装（JetBrains の one-dark プラグイン、akamud
の Atom 生成 VS Code 移植、joshdick/navarasu/olimorris の Vim/Neovim テーマ、
Sublime 移植、2 つの Emacs テーマ）を調べると、ある立場が広い合意なのか、
族のある系統の特徴なのか、他に例がないものなのかが分かる。決定を変えた知見は
第 III 部に記録した。調査ではまた、型＝黄がエコシステム全体で満場一致であること、
`${}` の暗赤が Atom に忠実なすべての移植に受け継がれていることも確認した。

### 4. 層構造: 字句的なものは TextMate に属し、セマンティックは訂正する

- 誤分類されえないもの（キーワード、文字列、数値、コメント、演算子、句読点）
  は TextMate に属する。そこでは正規表現で十分であり、TextMate は言語サーバが
  起動する前も Markdown のコードフェンス内でも動く。
- 誤分類されうるもの（識別子の役割: 変数か、型か、関数か）はセマンティック
  トークンで訂正する。
- したがって、TextMate が意図的に設定した色をセマンティックルールが塗り替える
  のはバグである。セマンティックルールにできるのは、TextMate が素の前景色の
  まま残したトークンを埋めること、または TextMate 自身の推測が間違っている
  箇所を直すことだけである。
- `npm run audit`（本物の文法 ＋ 本物の言語サーバ）がこれを機械的に強制する。
  TextMate とセマンティックの不一致は *flicker*（ちらつき）違反である。例外は
  `audit/allow.json` にだけあり、それぞれに理由が付いている。

この原則から導いた決定: セマンティックの `operator` エントリの削除（§9）、
`function.defaultLibrary` 修正の取り消し（§17）、定数統合を完成させたちらつき
違反（§10）。

### 5. 同一性: 同じシンボルには同じ色

色はシンボルが何であるかに付き、どこに書かれているかには付かない。

決定的な事例は One Dark Pro の黄いドットレシーバで、同じ変数がドットの前に
あるかどうかで色が変わる。私たちはこれを却下した（§12）。同じ原則で
`this`/`self` も決まる: これらは値なので、特別な色ではなく変数の赤を纏う
（§12）。

この原則と上流への忠実さ（§6）がぶつかったときは、この原則が勝つ。

### 6. 上流に対する実用主義

`atom/one-dark-syntax` からの忠実な再構築を一度試して、却下した。グレーの
パラメータ、前景色の演算子、暗いコメントは日常使用に耐えなかった。One Dark Pro
の約 150 の言語別ルールは、実際の文法に対する 10 年の調整の成果であり価値が
あるが、One Dark Pro は私たちが審査する依存関係であって、基準ではない。その
ルールは、出自の確認で弱い履歴のものが見つかるまでの間だけ有効だった（§3、
第 III 部）。One Dark Pro は最初は基準であり、次にルールごとに審査する依存関係
になり、今は複数ある参照元のひとつである。v0.1.0 以降、その変更は同期しない
（§19）。取り込む価値があるものは、他の参照元の立場と同じく、決定を経て入って
くる。

好みの判断の物差しは、この系統のテーマを長年日常的に使ってきて校正された目で
ある。その帰結を 2 つ、正直に記録しておく。私たちは One Dark Pro の特徴を 2 つ、
純粋に好みで残している: パラメータのイタリック（§12）と、証拠が退けるまで
長い間残していた定数＝黄（§10）。また、机上では正しいスキーム（オール素の
演算子、§9）を、実際に見て間違って見えたという理由で一度却下した。履歴が色を
提案し、日常使用が最終決定する。

### 7. 決定は理由付きで書き残す

色の理由は、チャットログやコミットメッセージではなく、機械可読な場所に置く:

- `audit/allow.json` — セマンティックが TextMate を上書きしてよい場所と、その
  理由
- `audit/jetbrains-expected.json` — 実際の IDE で保証される色と、文書化された
  相違
- このドキュメント — 原則と決定

これらを合わせたものが、これまでの決定の記録である。変更はまずこの記録と
照らし合わせる。

### 8. 仮定するな、計測せよ

色は知識、対応表、コーパスではなく、本物のエンジンに対して検証する:

- VS Code: `vscode-textmate` ＋ gopls / typescript-language-server
  （`npm run audit`）
- JetBrains: ヘッドレスの GoLand / WebStorm が、実際のトークン属性キーを
  フォールバックチェーンごとにダンプする（`jetbrains-audit/`）
- 2026 アクセント: 色相帯スキャンが 13 色のアクセント族の再対応を守る

仮定が外れることを示す、このリポジトリの履歴からの証拠: 慎重な手動監査が
組み込みの色を誤判定した。テーマコーパスによる確認が本当のキー
`GO_LOCAL_VARIABLE` を見落とした。もっともらしいセマンティックの「修正」が、
出荷前にハーネスで反証された（§17）。原則の変更が 3 件のちらつき違反を
引き起こし、それが一括修正で見落とされたただひとつのルールの位置を特定した
（§10）。一度起きたバグの種類には、すべて機械的な守りを付ける。

検証にかける労力は、テーマとピクセルの間にどれだけの知能が挟まっているかに
比例させる: IntelliJ > VS Code > Vim > ターミナル（受動的なパレット。生成の
正しさ以外に確認するものはない）。

## 第 III 部 — 決定

議論のあった決定を、トークン族ごとに記録する。各項目はまず決定を述べ、次に
その根拠と経緯を述べる。いくつかの決定は以前の決定を置き換えるため、分かって
いる日付は残している。

### 9. 演算子

- **記号演算子はすべての言語でシアン `#56B6C2`**（2026-07-20）。
  根拠: 演算子の族を分割する参照元はない。TextMate 時代の Atom はすべての
  演算子を紫にした。後期 Atom はすべて素のままにした。Zed はすべてシアンに
  する。base16 は演算子を base05（前景色）に分類する。後のエコシステム調査で、
  シアンは 3 つの有力な陣営（素/シアン/紫）のひとつで、akamud と One Dark
  Pro.nvim と共通だと分かった。
  経緯: One Dark Pro は混合を出荷していた（論理演算子はシアン、三項/
  オプショナルは単語演算子グループ経由で紫、アローは紫、残りは素）。この混合は
  出自の確認に通らず、一括で外した。机上では正しいオール素のスキームを先に
  出荷したが、同日に一目で取り消した。洗い流されたような演算子は日常使用に
  耐えず、代わりに Zed のオールシアンの立場を採用した。
- **`=>` はキーワードではなく演算子**（2026-07-20）。紫のアロー（TextMate-Atom
  と One Dark Pro）は現代の参照元に負けた。公式 tree-sitter クエリは `"=>"`
  を他のすべての記号と同じ `@operator` キャプチャに列挙している。
- **単語演算子は紫のまま**: `new`、`typeof`、`instanceof`、`in`、`of`、
  `delete`、`void`、Python の `and/or/not`。単語はキーワード、記号は演算子で、
  各族は内部で一様である。
- **型世界の記号は素のまま**: 注釈の `:`、オプショナルの `?`、ユニオンの `|`。
  Zed はこれらを暗赤（`punctuation.special`）に塗るが、それは Zed 独自の工夫で
  あり、取り込まなかった。
- **Go の演算子はひとつのシアンの族**（`:=` `+` `*` `&` `&&` `==`）。
  One Dark Pro の Go の癖（理由の書かれていない 2018 年のコミットによる `:=`
  の黄、2020 年のバグ報告パッチによるポインタの紫）は外した。後に汎用の演算子
  の決定が Go の `&&` を素のまま取り残しかけたとき、`.go` スコープのエントリで
  族を保った。
- **セマンティックの `operator` エントリは持たない。** rust-analyzer などの
  サーバが TextMate の言語ごとの演算子色を平坦化していたので、層構造の原則
  （§4）に従ってエントリを削除した。

### 10. 定数とリテラル

- **名前付き定数はオレンジの値の族に統合**（2026-07-20）: `const` ローカル、
  SCREAMING 定数、列挙メンバ、プラットフォーム定数（`Math.PI`、`JSON`）は
  すべて数値や真偽値と同じ `#D19A66` を纏う。この統合以降、黄が意味するのは
  ただひとつ、型の族である。
  根拠: 以前の黄への分割は、族の他のどの系統にもない One Dark Pro の特徴だった
  （エコシステムで分割する数少ないテーマはシアンや紫を使う）。base16 は定数と
  リテラルをまとめて base09 に分類する。
  経緯: 統合は当初 `variable.defaultLibrary` を黄のまま取り残していた。`JSON`
  に対する 3 件の新しいちらつき違反がそれを捕まえ、監査がリリース前に修正を
  強制した。原則の変更が、一括修正で見落とされたただひとつのルールの位置を
  特定した。
- **`nil`/`null`/`None` はオレンジ**: これらはリテラルである。Zed の黄い `nil`
  は二重に孤立している。黄を使う実装は他になく、Zed 自身のクエリは `nil` を
  `true`/`false` から分けているが、公式 tree-sitter クエリはその分割を明示的に
  否定している（`true`/`false`/`nil`/`iota` をひとつの `@constant.builtin`
  キャプチャにまとめている）。
- **JSON の真偽値はオレンジ**。One Dark Pro の言語別例外に対して、TextMate-Atom
  と Zed の一致を復元した（2026-07 の一貫性整理で発見、§17）。

### 11. 型

- **型の族は黄であり、黄は型の族だけである。** クラス、インターフェース、
  列挙型、名前空間、構造体、型パラメータ。Go の組み込みプリミティブ型
  （`int`、`string`、`error`）を含む: 型が黄なのは型だからであって、綴り方の
  せいではない。（Go のプリミティブ型は 2026-07 の整理まで紫だった、§17。）
- **Zed の型シアンは正当な系譜だが、採用しない。** 履歴を掘ったことで以前の
  結論が訂正された: シアンの型は base16 テンプレートの産物ではない。
  tree-sitter 時代の Atom 自身が型をシアンで描画しており
  （`type_identifier → support.storage.type`）、Zed の 2023 年の手動調整は
  意図的にそれを残した。黄もシアンも、時代の異なる Atom の系譜である。この
  テーマのスタック（TextMate 文法 ＋ 言語サーバ）は TextMate 世代の子孫で、
  エコシステム調査でも型＝黄が 8 実装すべてで満場一致だったので、黄を維持する。

### 12. 変数、キー、パラメータ

- **変数の族は赤**、`this`/`self` を含む。これらは値なので、特別な色ではなく
  変数の赤を纏う（§5）。現代の tree-sitter オントロジーからの異議（区別として
  `@variable.builtin` がある）は記録に残っているが、私たちは同一性の立場を
  取った。（2026-07 の整理まで型の黄を纏っていた、§17。）
- **ドットレシーバとチェーン途中のプロパティは普通の変数。** One Dark Pro は
  ドットのレシーバを黄に塗る（`variable.other.object`）ので、同じ変数がドットの
  前にあるかどうかで色が変わる。私たちは同一性の原則（§5）でこれを却下した。
  `a.b.c` の `b` も同じ決定に従う。One Dark Pro がこのルールで望んだもの、
  つまりコンテナ的なものが黄に見えることは、セマンティックの namespace と
  class のルールで正直に達成できる。結果として生じる TextMate とセマンティック
  の不一致は `allow.json` の恒久的なエントリである。
- **キーの族はフォーマットを横断して赤**: JSON キー、YAML キー、CSS プロパティ
  名（CSS のエントリは Zed を参照元として族の穴を塞いだ）、TOML の配列キー。
  One Dark Pro の名残が TOML の配列キーを型の黄に塗っていた。セマンティック
  ルールが族名で書かれるようになった瞬間にそれが表に出た。「tomlArrayKey:
  type」は、「#e5c07b」ではそう読めなかった形で、間違いとして読めるからだ。
  ベンダープレフィックス付きの CSS プロパティ（`-webkit-*`）はシアンのまま:
  ベンダープレフィックスはプラットフォームが提供するものである。
- **パラメータは赤のイタリック。** エコシステム調査でこれは One Dark Pro の
  特徴だと分かった（赤は一般的だが、イタリックはそうではない）。私たちは
  意図的に残し、出自ではなく好みとして記録する（§6）。Python 専用のパラメータ
  色は族に対する例外で、2026-07 に外した（§17）。

### 13. 埋め込み境界と文字列

- **`${}` と埋め込みの句読点は暗赤 `#BE5046`**。TextMate-Atom の全 78 割り当て
  を機械的に照合した後、起源に戻した。
  根拠: 起源、base16 の 0F スロット（「embedded language tags」）、Atom に
  忠実なすべての移植（akamud、joshdick、Sublime）が一致する。
  経緯: tree-sitter 時代の Atom はこの色を失った（移行時に波括弧の対応付けが
  なかったので、決定ではなく移行時の損失）。One Dark Pro は一度も持たなかった。
  JSX 式の波括弧も同じスコープと同じ意味、つまり言語と言語の境界を持ち、
  ワークベンチの括弧深度サイクルから意図的に除外している。
- **`variable.interpolation` は暗赤**: 同じ族。
- **正規表現はシアン。** One Dark Pro の赤は VS Code Dark+ を真似た 2022 年の
  意図的な変更で（issue #678）、Dark+ を真似ることはこのテーマの目的ではない。
  5 つの参照元のスコアは僅差の 3 対 2 だった（現代の世代は正規表現を「特殊な
  文字列」、つまりオレンジと読む）。エコシステム調査（JetBrains、akamud、
  Sublime がすべてシアン）が差を広げ、この問題を閉じた。
- **Markdown のリンク URL はシアン**（起源の復元、`${}` と同じ照合による）。
- **HTML エンティティはオレンジ**（説明のない 2017 年の One Dark Pro の編集に
  対して、Atom と Zed が二世代にわたって一致）。
- **CSS の単位はオレンジ。** One Dark Pro の赤は 2018 年の外部からの一括 PR に
  遡り、ジェネレータの書き直しで焼き込まれたもので、作者自身の設計ですらない。

### 14. マークアップ

- **タグは赤、属性はオレンジ**: 参照元とエコシステムでほぼ満場一致（base16 は
  「XML Tags」を base08 の赤に分類する）。Zed の青いマークアップ族は Zed 独自の
  設計方針で、廃止された Zed バリアントにだけ残っている（付録 A）。
- **見出しは赤**（One Dark の伝統。一部の派生が使うシアンではない）。

### 15. シェル

- **コマンド名は緑、フラグ（`constant.other.option`）はシアン、引用符なしの
  引数は素のまま**: zsh-syntax-highlighting に合わせたターミナルの見た目。
  この緑は族のルールに対して認めた 2 つの例外のひとつで（§2）、2026-07 の
  整理で見直したうえで残した。

### 16. ワークベンチ（UI 層）

- **アイコンの色は VS Code のデフォルトのまま**（2026-08-12）。これはシンタックス
  テーマである。UI 層に手を入れるのは、何かが本当に見づらいか紛らわしいときだけ
  で、トークン語彙との一貫性のためだけには触らない。VS Code のアイコンパレット
  は暗いワークベンチ上で読めるので、`symbolIcon.*` や他のアイコンキーはテーマ化
  しない。アイコンがトークンと同じ分類を描画しているとしてもだ。
- **同じ基準で `scmGraph` の色覚多様性に配慮したパレット、チャート、マージ/
  diff の状態色もデフォルトのままにしている。**
- **2026 のアクセント再対応はこの基準を満たす**: 上流のティールがシンタックスの
  シアン `#56B6C2` とぶつかるので、13 色のアクセント族を `#528BFF` に再着色する
  （色相帯スキャンが守る、§8）。

### 17. 私たちが訂正した間違い

このプロジェクトが間違え、後に公開の場で直した結論。自分たちの決定を再確認する
ことは方法の一部なので、ここに残す。

一貫性の整理（2026-07）。このドキュメントそのものに対してテーマを監査した
ところ、自分のルールを破っている箇所が 5 つ見つかった:

1. TypeScript の型は黄なのに Go のプリミティブ型が紫 — 修正（§11）。
2. `this`/`self` が型の黄を纏う — 修正（§12）。
3. Python パラメータの言語別例外色 — 修正（§12）。
4. JSON 真偽値の言語別例外色 — 修正（§10）。
5. シェルのコマンド名が緑 — 見直したうえで維持（§15）。

遅れて見つかったもの: Dart 専用の 4 件のセマンティック例外（One Dark Pro の
名残）は、族名による命名で見えるようになった時点で外した。Python パラメータと
同じ判断である。教訓: 層の一貫性（ちらつき監査が調べるもの）は族の一貫性では
ない。前者を満たしていても、後者は壊れたままでありうる。

個別の訂正:

- 「Zed は LSP セマンティックハイライトをサポートしていない」— 古い情報。
  2026 年 2 月にオプトインで入った。Zed バリアントは `"combined"` モードを
  モデル化した（付録 A）。
- 「型シアンは base16 テンプレートの産物」— 半分間違い。§11 を参照。
- 「One Dark Pro の正規表現の赤は偶然」— 意図的な Dark+ の模倣だった。却下の
  理由は変わるが、結果は変わらない（§13）。
- 「Zed の正規表現オレンジは他に例がない」— 現代の tree-sitter オントロジーと
  同じ側に立っている。シアンの決定は別の根拠で維持する（§13）。
- `function.defaultLibrary` のシアン「修正」は短期間出荷して取り消した:
  ちらつきハーネスが、それがちらつきを取り除くどころか持ち込むことを示した
  （§4、§8）。
- オール素の演算子スキームは短期間出荷して取り消した。日常使用で間違いだと
  分かった（§9）。

## 第 IV 部 — 構成と運用

### 18. 唯一の真実の源、あらゆる場所へ生成

ビルドされた VS Code テーマ（`themes/*.json`）が、すべてのプラットフォームに
とっての唯一の真実の源である。JetBrains の `.icls`、Ghostty、Windows Terminal、
Vim の成果物は One Dark 2026 から生成される（`scripts/lib.ts`、
`loadBuiltTheme`）ので、16 進値の一致は構造的に保証される。これらは
「One Dark Modern」というスキーム名を保つ。これは拡張機能のアイデンティティ
であって、バリアントのラベルではない。

- 生成ファイル（`themes/`、`dist/`）は手で編集しない。CI が再現性を検証する。
- 手で編集する面は `syntax/`、`overrides/`、そして `audit/` 配下の決定記録
  だけである。

### 19. シンタックス層は所有し、UI 層は差分をとる

シンタックスには上流がない。v0.1.0 以降、`syntax/` はこのリポジトリ自身の
真実の源である。`families.json` は §2 の語彙を 16 進値に対応付け、`tokens.json`
と `semantic.json` のルールは族を名前で参照する。したがって色はちょうどひとつの
場所にあり、ビルドは語彙の外の色を持つルールやセマンティックエントリを拒否
する。

どう同梱したか。ルールはビルド済みテーマから同梱した。出力がバイト単位で同一で
あることは機械で検証済みである。One Dark Pro の 10 年の文法調整を完全に吸収し、
議論のあったルールのすべてを出自プロセス（§3、§6、第 III 部）で確認または
削除した後のことだ。続く v0.1.1 のリファクタリングでは、同じ族のルールを統合し、
死んだ重複を削除することで、同梱ルールを 288 から 14 に圧縮した。各ステップは
本物の TextMate エンジンに対して検証した: 6,762 のフィクスチャトークンと 464
のセレクタすべてで同一の解決。

UI 層は差分である。`overrides/` は Dark Modern / 2026 Dark に対する UI 層の差分
だけを持つ。これらは引き続き生きた上流である。エントリを残すかどうかのテスト
は: これを削除したら、テーマのコンセプトは損なわれるか？ 損なわれないなら上流に
委ねる。オーバーライドが小さいほど、週次の自動同期の見返りは大きい。

### 20. プラットフォームの限界

プラットフォームが表現できない区別は、戦わずに相違として文書化する
（`audit/jetbrains-expected.json`）:

- IntelliJ には TypeScript 向けの const/readonly キーがない → そこでは const は
  赤のまま
- PyCharm にはパラメータ専用のキーがない → `DEFAULT_PARAMETER`（赤の
  イタリック）が代役を務める
- Pylance はクローズドソース → Python のセマンティック層は自動検証の外側
  （目視でカバー）

### 21. 運用

- 上流の同期。UI の上流（Dark Modern、2026 Dark）は CI にゲートされた PR を
  通じて週次で同期し、その PR は自身でマージしリリースする。シンタックスには
  上流がなく、同期で変わることはない。同期を止めるには、その PR を閉じる。
- 保守ループ。(a) 不一致をスクリーンショットし、(b) `syntax/` または
  `overrides/` を調整し、(c) 決定を第 III 部に記録する。
- リリース。手動リリースは `npm version patch`。どちらにせよ 5 つの
  プラットフォーム成果物が自動的に出荷される。

## 付録 A. Zed のエピソード: 計測器としての忠実さ

v0.0.x の一時期、このリポジトリは Zed の One Dark 解釈をそのまま再現した 2 つの
テーマも出荷していた。このドキュメントの決定が却下する部分（青いマークアップ、
シアンの型、黄の `nil`）も含めてである。その約束は判断ではなく忠実さだった:
Zed のテーマスロットとセマンティックルールファイルを機械的に翻訳し、Zed 自身が
同梱するクエリを使った実際の tree-sitter パースに対してトークン単位で検証し
（5,000 以上のキャプチャ、不一致ゼロ）、Zed が未指定のまま残した部分には
「隙間埋めは可、バグは不可」のルールを適用した。Zed がオプトインの LSP
セマンティックハイライトをサポートすると分かってからは、Zed の `"combined"`
モードをモデル化した（§17）。

バリアントは v0.1.0 で廃止したが、このエピソードは原則を形作った。Zed の解釈の
中で暮らすことで、第 III 部で決めた演算子、マークアップ、型の族の問題の大半が
浮上し、忠実な再現は計測器として機能した。「我々の色と Zed の色、どちらが
正しいか」という議論のいくつかは、両方の描画を並べることで決着した。Zed の
解釈が欲しい人は Zed で Zed のテーマを使えばよい。他のエディタの判断を再現する
ことは研究の道具であって、製品ではない。

## 付録 B. 用語集

- One Dark Pro — このリポジトリがその言語ルールを吸収し、その後ルールごとに
  審査した VS Code テーマ（§6）。
- TextMate — VS Code が字句ハイライトに使う正規表現ベースの文法層。言語サーバ
  なしで動く（§4）。
- セマンティックトークン / LSP — 言語サーバが供給する役割情報（変数、型、
  関数）。TextMate の上に重ねる（§4）。
- Flicker（ちらつき）— TextMate の色とセマンティックの色が食い違うトークン。
  言語サーバが起動すると目に見えて色が変わる。`npm run audit` の層構造検査の
  単位（§4）。
- base16 — Kempson の 16 スロット配色標準。スロットの役割が文書化されている
  ので、意味の議論の基準になる（§3）。
- 参照元 — 出自の確認で参照する One Dark の 5 つの世代のひとつ（§3）。
- 族 — `syntax/families.json` に名前で定義された意味のグループ。色を割り当てる
  単位（§2）。
- `allow.json` — 認められた TextMate とセマンティックの不一致の一覧。それぞれに
  理由が付く（§7）。
- Dark+ / Dark Modern / 2026 Dark — VS Code 自身のデフォルトのダークテーマ。
  Dark Modern と 2026 Dark はこのテーマのワークベンチ UI を供給し、Dark+ は
  かつて One Dark Pro が真似した対象としてだけ関係する（§13）。
- ワークベンチ — VS Code の UI クローム（サイドバー、タブ、ターミナル）。
  エディタのシンタックス色と対をなす（§1、§16）。
